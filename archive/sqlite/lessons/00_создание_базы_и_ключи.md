# Урок 0. Создаём базу своими руками: ключи, ограничения, транзакции

## Зачем этот урок

Дальше в курсе вы будете работать с готовой базой `trading_training.db`. Но если начать
сразу с готовой базы, легко выучить синтаксис SQL, так и не поняв, **почему база устроена
именно так**: почему у каждой сделки есть `instrument_id`, а не просто текст "SBER"; почему
нельзя вставить сделку на несуществующий инструмент; почему нельзя случайно продублировать
инструмент с тем же ID.

Поэтому идея урока такая: **сначала вы своими руками строите маленькую базу с нуля, ломаете
её экспериментами и смотрите на реальные ошибки SQLite — а уже потом переходите к готовой
торговой базе.**

Все команды в этом уроке нужно набирать самостоятельно в `sqlite3`. Ничего не выполняется
"автоматически" — это принципиально: ошибка, которую вы вызвали своими руками и увидели
своими глазами, запоминается совсем не так, как прочитанное объяснение.

## 1. Создаём свою базу

Откройте терминал в папке `sql_trader_starter` и выполните:

```cmd
sqlite3 lesson_00.db
```

Если файла `lesson_00.db` не было — SQLite создаст его в момент, когда вы первый раз
реально запишете туда данные (создадите таблицу). Пустой файл на диске появится не сразу
после запуска команды, а после первой операции записи — это нормальная особенность SQLite,
не ошибка.

Вы должны увидеть приглашение:

```text
sqlite>
```

Это означает, что вы находитесь внутри интерактивной сессии `sqlite3`, подключённой к файлу
`lesson_00.db`. Дальше есть два вида команд:

- **SQL-команды** — универсальный язык запросов, работает одинаково (с небольшими отличиями)
  в SQLite, PostgreSQL, MySQL и других базах. Всегда заканчиваются точкой с запятой `;`.
- **Точечные команды `sqlite3`** (dot-commands) — это команды именно консольной утилиты
  `sqlite3.exe`, а не языка SQL. Они не работают в других СУБД и не требуют `;`.

Попробуйте:

```sql
.databases
```

Вы увидите путь к файлу `lesson_00.db` — это подтверждение, что вы подключены именно к нему.

```sql
.tables
```

Список будет пустым — в базе пока нет ни одной таблицы.

```sql
.schema
```

Тоже пусто — схема (то есть набор описаний всех таблиц, индексов и правил в базе) ещё не
существует.

### Ключевые понятия

| Термин | Что это такое |
|---|---|
| SQLite | Программа-библиотека, которая умеет хранить и обрабатывать данные в одном файле, без отдельного сервера |
| Файл `.db` | Обычный файл на диске, в котором SQLite хранит все таблицы, индексы и данные |
| База данных | Организованное хранилище данных: набор таблиц, связанных между собой |
| Схема (schema) | Описание структуры базы: какие есть таблицы, какие в них колонки, какие правила (ключи, ограничения) |
| Таблица | Набор однотипных записей, организованных в строки и колонки. Например, таблица `instruments` хранит инструменты |
| Строка (row) | Одна конкретная запись в таблице. Например, одна строка — это один конкретный инструмент SBER |
| Колонка (column) | Один именованный атрибут, общий для всех строк таблицы. Например, колонка `ticker` есть у каждой строки в `instruments` |
| Значение (value) | Конкретное содержимое одной ячейки — на пересечении строки и колонки. Например, значение колонки `ticker` в строке SBER — это текст `'SBER'` |
| SQL | Язык, на котором мы описываем, что хотим сделать с данными (создать таблицу, вставить строку, выбрать данные) |

Важное отличие: `.tables`, `.schema`, `.databases` — это удобные ярлыки самой программы
`sqlite3.exe` для быстрого просмотра. SQL-запрос, который делает почти то же самое для
таблиц — `SELECT name FROM sqlite_master WHERE type = 'table';` — сработает в любом
SQL-клиенте, а `.tables` — только в консоли `sqlite3`.

## 2. CREATE TABLE и типы данных

Создадим первую таблицу — справочник финансовых инструментов:

```sql
CREATE TABLE instruments (
    instrument_id INTEGER PRIMARY KEY,
    ticker        TEXT NOT NULL UNIQUE,
    name          TEXT NOT NULL
);
```

Проверим:

```sql
.tables
.schema instruments
```

### Типы данных SQLite

SQLite поддерживает 5 базовых типов хранения (storage classes):

| Тип | Для чего | Пример из нашей БД |
|---|---|---|
| `INTEGER` | Целые числа | `instrument_id`, `quantity` |
| `REAL` | Числа с плавающей точкой | `price`, `close_price` |
| `TEXT` | Текст | `ticker`, `name`, `side` |
| `NULL` | Отсутствие значения (не ноль, не пустая строка — именно "значение неизвестно/не задано") | пустая ячейка, которую ничем не заполнили |
| `BLOB` | Бинарные данные "как есть" (файлы, изображения). В этом курсе почти не используется — финансовым данным он обычно не нужен | — |

### Важная особенность SQLite: гибкость типов (type affinity)

В отличие от PostgreSQL или MySQL, SQLite не требует, чтобы в колонке `TEXT` обязательно
лежал текст, а в `INTEGER` — обязательно число. SQLite использует понятие
**type affinity** ("тяготение к типу"): тип колонки — это *подсказка/предпочтение*, а не
жёсткий запрет. Если вы попробуете записать текст в колонку с типом `INTEGER`, SQLite
попытается преобразовать его в число; если преобразовать не получится — сохранит как есть.

Это удобно для новичка (меньше ошибок на старте), но и опасно: опечатка не всегда будет
поймана на уровне типа колонки. Именно поэтому в реальных финансовых таблицах мы будем
дополнительно использовать `CHECK`, `NOT NULL` и `FOREIGN KEY` — они дают куда более строгий
контроль, чем один только тип колонки. Подробнее об этом — дальше в этом уроке.

## 3. PRIMARY KEY — зачем он нужен на самом деле

Добавим три инструмента:

```sql
INSERT INTO instruments (instrument_id, ticker, name) VALUES (1, 'SBER', 'Сбербанк');
INSERT INTO instruments (instrument_id, ticker, name) VALUES (2, 'GAZP', 'Газпром');
INSERT INTO instruments (instrument_id, ticker, name) VALUES (3, 'LKOH', 'Лукойл');

SELECT * FROM instruments;
```

Вы увидите три строки. Теперь — **эксперимент**. Попробуйте добавить ещё один инструмент,
но по ошибке (как будто случайно скопировали код и забыли поменять ID) укажите тот же
`instrument_id`, что уже занят:

```sql
INSERT INTO instruments (instrument_id, ticker, name) VALUES (1, 'ROSN', 'Роснефть');
```

Вы получите ошибку:

```text
Runtime error: UNIQUE constraint failed: instruments.instrument_id
```

### Почему это критично важно, а не просто "красивое правило"

Представьте на секунду, что этой ошибки не произошло бы и запись всё-таки записалась бы.
Тогда в таблице `instruments` было бы **две разные строки с `instrument_id = 1`**: одна —
`SBER`, другая — `ROSN`. Теперь задайте себе вопрос: если где-то в таблице сделок встретится
`instrument_id = 1`, к какому инструменту относится эта сделка — к Сбербанку или к
Роснефти? **Ответить невозможно.** Ссылка стала неоднозначной.

Именно это и решает `PRIMARY KEY`: он гарантирует, что `instrument_id = 1` **однозначно** и
**навсегда** означает ровно один конкретный инструмент во всей базе. Это не абстрактное
"обеспечивает уникальность" — это конкретная защита от ситуации, в которой вы физически не
сможете понять, о какой сделке идёт речь.

`PRIMARY KEY` в SQLite совмещает два свойства:
1. **Уникальность** — значение не может повторяться в разных строках.
2. **NOT NULL** (для большинства случаев, см. ниже про `INTEGER PRIMARY KEY`) — то есть у
   каждой строки обязательно должен быть свой ключ, пустых ключей быть не может.

## 4. UNIQUE — тот же принцип, но не для главного ключа

Теперь попробуем нарушить другое правило — уникальность тикера:

```sql
INSERT INTO instruments (instrument_id, ticker, name) VALUES (4, 'SBER', 'Дубликат Сбербанка');
```

Ошибка:

```text
Runtime error: UNIQUE constraint failed: instruments.ticker
```

### PRIMARY KEY против UNIQUE — в чём разница

И `PRIMARY KEY`, и `UNIQUE` не позволяют повторять значение в колонке. Но:

- В таблице может быть **только один** `PRIMARY KEY` (возможно, состоящий из нескольких
  колонок сразу — про это будет отдельный раздел про составные ключи).
- `UNIQUE`-ограничений может быть **сколько угодно**, на разных колонках.
- `PRIMARY KEY` — это "главный", основной идентификатор строки, к которому обычно строятся
  внешние ключи из других таблиц (см. раздел про `FOREIGN KEY`).
- `UNIQUE` говорит: "это значение не должно повторяться", но не обязательно делает колонку
  главным идентификатором.

В нашем случае `instrument_id` — это **технический ID**: число, которое ничего не значит
само по себе, кроме факта уникальности. `ticker` — это **бизнес-идентификатор**: значение,
которое имеет смысл для человека (трейдера, бухгалтера) и по которому реально ищут
инструмент в реальной жизни.

Похожая идея есть и в реальном финансовом мире: у инструмента может быть внутренний
технический ID в конкретной системе, тикер на конкретной бирже (может отличаться для разных
площадок) и **ISIN** — международный стандартный номер ценной бумаги, который остаётся
одним и тем же в разных странах и системах. Не существует единственно правильного ответа,
какой из идентификаторов "главный" — это зависит от задачи. В учебных целях мы используем
простой числовой `instrument_id` как технический ключ, а `ticker` защищаем через `UNIQUE`,
потому что в реальной торговле дубликат тикера — это почти всегда ошибка данных.

## 5. INTEGER PRIMARY KEY и rowid

У SQLite есть специфика, которой нет в большинстве других СУБД. Вставим инструмент **без**
явного указания `instrument_id`:

```sql
INSERT INTO instruments (ticker, name) VALUES ('ROSN', 'Роснефть');

SELECT * FROM instruments;
```

Вы увидите, что `instrument_id` заполнился автоматически (скорее всего, значением `4`) —
хотя мы его вообще не указывали.

### Почему так произошло

В SQLite у каждой обычной таблицы есть скрытая системная колонка `rowid` — внутренний
номер строки. Когда вы объявляете колонку как `INTEGER PRIMARY KEY` (именно так: тип
`INTEGER`, ровно одна колонка, без составного ключа), SQLite делает эту колонку **псевдонимом
`rowid`**. Это значит:

- Если вы не указали значение при `INSERT`, SQLite сам подберёт следующее свободное целое
  число.
- Обращение к `instrument_id` — это фактически прямое обращение к внутреннему номеру строки,
  что делает поиск по первичному ключу очень быстрым.

Мы **намеренно не использовали** `AUTOINCREMENT` (`INTEGER PRIMARY KEY AUTOINCREMENT`).
Разница: обычный `INTEGER PRIMARY KEY` может повторно использовать номера, оставшиеся от
удалённых строк, а `AUTOINCREMENT` гарантирует, что номер никогда не выдаётся повторно за всю
историю таблицы, даже после удаления строк — ценой дополнительных накладных расходов. Для
учебных целей и для большинства реальных задач разница не критична, а `AUTOINCREMENT` — это
осознанный выбор, который нужно делать понимая компромисс, а не "по умолчанию для
надёжности".

## 6. FOREIGN KEY — контроль ссылок между таблицами

Прежде чем создавать таблицы со ссылками друг на друга, нужно включить проверку внешних
ключей. Это **обязательный шаг** в SQLite — без него ограничения `FOREIGN KEY` будут просто
записаны в схеме, но реально проверяться не будут.

```sql
PRAGMA foreign_keys;
```

Скорее всего вы увидите `0` — по умолчанию проверка выключена. Включаем:

```sql
PRAGMA foreign_keys = ON;

PRAGMA foreign_keys;
```

Теперь должно быть `1`.

**Важно понимать:** `PRAGMA foreign_keys` относится не к базе данных как файлу, а к
**конкретному соединению** (подключению) с базой. Если вы закроете `sqlite3` и откроете
`lesson_00.db` заново — придётся снова выполнить `PRAGMA foreign_keys = ON;`. В файле
`01_create_database.py` мы включаем этот `PRAGMA` в коде Python при каждом подключении именно
по этой причине.

Теперь создадим таблицу сделок со ссылкой на инструмент:

```sql
CREATE TABLE trades (
    trade_id      INTEGER PRIMARY KEY,
    instrument_id INTEGER NOT NULL,
    side          TEXT NOT NULL CHECK (side IN ('BUY', 'SELL')),
    quantity      INTEGER NOT NULL CHECK (quantity > 0),
    price         REAL NOT NULL CHECK (price > 0),

    FOREIGN KEY (instrument_id) REFERENCES instruments(instrument_id)
);
```

Добавим корректную сделку:

```sql
INSERT INTO trades (trade_id, instrument_id, side, quantity, price)
VALUES (1, 1, 'BUY', 10, 280.50);
```

Сработало, потому что `instrument_id = 1` (SBER) реально существует в таблице
`instruments`. Теперь **эксперимент** — попробуем сослаться на несуществующий инструмент:

```sql
INSERT INTO trades (trade_id, instrument_id, side, quantity, price)
VALUES (2, 999, 'BUY', 10, 100);
```

Ошибка:

```text
Runtime error: FOREIGN KEY constraint failed
```

`instrument_id = 999` нигде не существует в `instruments` — и SQLite не дал создать сделку
"в никуда".

## 7. Главное: FOREIGN KEY — это НЕ JOIN

Это принципиально важно понять именно сейчас, до знакомства с настоящим `JOIN` в уроке 4.

`FOREIGN KEY` **не делает** следующего:

- не показывает тикер рядом со сделкой;
- не "соединяет" строки из `trades` и `instruments` в один результат;
- не выполняет `JOIN`;
- не создаёт отсутствующую строку в `instruments`, если её там не было;
- не "угадывает", какой инструмент имелся в виду.

Всё, что делает `FOREIGN KEY` — это **проверка на входе**: разрешает запись, если ссылка
существует, и отказывает, если её нет. Это правило целостности данных, а не инструмент
получения данных.

Если вы прямо сейчас выполните:

```sql
SELECT * FROM trades;
```

— вы увидите `instrument_id = 1`, но **не увидите** тикер `SBER`. `FOREIGN KEY` не выводит
эту информацию на экран — он лишь не дал бы вам создать сделку, если бы такого
`instrument_id` не существовало.

## 8. Ручной JOIN — руками, до автоматического JOIN

Чтобы понять, зачем в принципе нужен `JOIN`, сделаем его **вручную**, глазами.

```sql
SELECT trade_id, instrument_id, side FROM trades;
```

Вы видите: `trade_id = 1`, `instrument_id = 1`, `side = BUY`. Теперь посмотрим, что такое
`instrument_id = 1`:

```sql
SELECT instrument_id, ticker FROM instruments;
```

Вы находите глазами строку `1 | SBER` и делаете вывод сами: **сделка №1 — это покупка
SBER.** Это и есть, по сути, "ручной JOIN" — вы сопоставили строку из одной таблицы со
строкой из другой по совпадающему значению ключа.

Именно эту работу — "найти совпадающий `instrument_id` и подставить рядом нужные колонки" —
позже за вас будет автоматически делать оператор `JOIN` (урок 4). Важно, что вы сначала
поняли **что** он делает вручную, прежде чем учить **синтаксис**, которым это делается
автоматически.

## 9. Ограничения (constraints): ломаем каждое по очереди

Мы уже видели `UNIQUE` и `FOREIGN KEY` в действии. Проверим оставшиеся: `NOT NULL` и
`CHECK`.

### NOT NULL

```sql
INSERT INTO instruments (instrument_id, ticker, name) VALUES (5, 'TEST', NULL);
```

Ошибка:

```text
Runtime error: NOT NULL constraint failed: instruments.name
```

Что произошло: мы попытались записать инструмент без названия. Правило `name TEXT NOT NULL`
в `CREATE TABLE` запрещает такую запись — колонка `name` обязана быть заполнена у каждой
строки. Строка не появилась в базе.

### CHECK — недопустимая сторона сделки

```sql
INSERT INTO trades (trade_id, instrument_id, side, quantity, price)
VALUES (3, 1, 'ABC', 10, 100);
```

Ошибка:

```text
Runtime error: CHECK constraint failed: side IN ('BUY', 'SELL')
```

Современные версии SQLite (как установленная у вас) показывают в тексте ошибки само
условие, которое было нарушено — это удобно, не нужно даже открывать `.schema`, чтобы понять,
какое именно правило сработало.

Мы пытались записать `side = 'ABC'`, а правило `CHECK (side IN ('BUY', 'SELL'))` разрешает
только два конкретных значения. `'ABC'` не является ни покупкой, ни продажей — это
бессмысленное для бизнеса значение, и `CHECK` не дал ему попасть в таблицу.

### CHECK — отрицательное количество

```sql
INSERT INTO trades (trade_id, instrument_id, side, quantity, price)
VALUES (4, 1, 'BUY', -5, 100);
```

Ошибка:

```text
Runtime error: CHECK constraint failed: quantity > 0
```

Мы пытались записать сделку с `quantity = -5`. Отрицательное количество бумаг в сделке не
имеет экономического смысла (для отражения продажи есть отдельное поле `side = 'SELL'`, а
не отрицательное число) — правило `CHECK (quantity > 0)` это запрещает.

### DEFAULT

`DEFAULT` — это не запрет, а "подстановка по умолчанию", если значение не указано явно.
Добавим новую колонку с значением по умолчанию:

```sql
ALTER TABLE trades ADD COLUMN commission REAL NOT NULL DEFAULT 0;

INSERT INTO trades (trade_id, instrument_id, side, quantity, price)
VALUES (5, 1, 'SELL', 10, 285.00);

SELECT * FROM trades WHERE trade_id = 5;
```

Мы не указали `commission` явно — SQLite подставил `0` автоматически, потому что мы задали
`DEFAULT 0` при добавлении колонки.

### Что происходит после каждой ошибки — важный вывод

После **каждой** из этих ошибок обратите внимание на общий паттерн:

1. Мы пытались записать что-то конкретное (например, `side = 'ABC'`).
2. Было нарушено конкретное правило (например, `CHECK (side IN ('BUY','SELL'))`).
3. Строка **не появилась** в таблице — база осталась в том состоянии, в котором была до
   попытки записи. Проверьте это сами: `SELECT * FROM trades WHERE trade_id = 3;` вернёт
   пустой результат — такой строки просто нет.

Ограничения (`constraints`) — это не "лишняя бюрократия". Это единственная причина, по
которой в реальной финансовой базе не может оказаться сделки с несуществующим инструментом,
бессмысленной стороной сделки или отрицательным количеством бумаг.

## 10. Связь один-ко-многим (one-to-many, 1:N)

Посмотрите на то, что уже получилось:

```sql
SELECT instrument_id, COUNT(*) AS trades_count
FROM trades
GROUP BY instrument_id;
```

(Здесь мы забежали немного вперёд по синтаксису — `GROUP BY` подробно разберём в уроке 3.
Сейчас важна не механика запроса, а сам факт, который он показывает.)

Вы увидите, что `instrument_id = 1` (SBER) встречается в `trades` несколько раз, при этом в
таблице `instruments` строка с `instrument_id = 1` — **ровно одна**.

Это и есть связь **один-ко-многим**: один инструмент — много сделок по нему. Формально это
записывают как `1:N`. Именно поэтому:

- `instrument_id` **уникален** в `instruments` (это её `PRIMARY KEY`);
- `instrument_id` **свободно повторяется** в `trades` (там это просто `INTEGER`, без
  `UNIQUE`) — иначе по одному инструменту нельзя было бы совершить вторую сделку.

Кратко о двух других типах связей, которые вы встретите позже:

- **Один-к-одному (1:1)** — редкий случай, когда каждой строке одной таблицы соответствует
  ровно одна строка другой (например, у сделки мог бы быть ровно один документ-подтверждение).
- **Многие-ко-многим (N:M)** — например, "один трейдер может управлять несколькими счетами, и
  одним счётом могут управлять несколько трейдеров". Такая связь требует отдельной
  промежуточной таблицы. Подробно эту тему мы не разбираем в этом курсе — достаточно знать,
  что она существует.

## 11. Изменение данных: INSERT, accou, DELETE

`INSERT` мы уже использовали много раз. Посмотрим на `UPDATE` и `DELETE`.

```sql
UPDATE trades
SET price = 300.00
WHERE trade_id = 1;

SELECT * FROM trades WHERE trade_id = 1;
```

Цена сделки №1 изменилась. Обратите внимание на структуру: **что менять** (`SET ...`) и
**у каких именно строк** (`WHERE ...`).

### Опасность отсутствующего WHERE

Это одна из самых важных практических вещей в этом уроке. Сравните две команды:

```sql
DELETE FROM trades WHERE trade_id = 1;
```

— удаляет **ровно одну** строку, с `trade_id = 1`.

```sql
DELETE FROM trades;
```

— без `WHERE` удаляет **абсолютно все** строки таблицы `trades`. То же самое верно и для
`UPDATE`: `UPDATE trades SET price = 0;` без `WHERE` изменит цену **у всех сделок сразу**.

Мы сейчас безопасно продемонстрируем именно эту опасность — но обернём её в транзакцию,
чтобы можно было откатить последствия. Это заодно первое знакомство с транзакциями.

---

## 12. Транзакции: BEGIN, ROLLBACK, COMMIT

Сначала посмотрим, сколько сейчас сделок:

```sql
SELECT COUNT(*) FROM trades;
```

Запомните это число. Теперь безопасно, "под контролем", устроим катастрофу и отменим её:

```sql
BEGIN;

DELETE FROM trades;

SELECT COUNT(*) FROM trades;
```

Вы увидите `0` — все сделки как будто исчезли. Но мы ещё не зафиксировали изменения.
Отменяем всё:

```sql
ROLLBACK;

SELECT COUNT(*) FROM trades;
```

Число сделок вернулось к исходному — как будто `DELETE FROM trades;` никогда не выполнялся.

Теперь пример, где мы, наоборот, **фиксируем** изменение:

```sql
BEGIN;

UPDATE instruments
SET name = 'Сбербанк, ПАО'
WHERE instrument_id = 1;

COMMIT;

SELECT * FROM instruments WHERE instrument_id = 1;
```

После `COMMIT` изменение сохранено окончательно — `ROLLBACK` после `COMMIT` уже не отменит
его (транзакция закрыта).

### Главная идея (без углубления в ACID)

- `BEGIN` — открывает "черновик" изменений.
- Всё, что вы делаете после `BEGIN`, можно **either** отменить целиком (`ROLLBACK`), **or**
  зафиксировать целиком (`COMMIT`).
- Пока не было `COMMIT`, изменения можно безопасно "отыграть назад".

Именно транзакции делают возможным то, что мы только что сделали: безопасно проверить, что
случится при "опасной" команде без `WHERE`, и тут же откатить результат, если он не понравился.

## 13. DELETE и FOREIGN KEY — база защищает от "сирот"

Попробуем удалить инструмент, на который есть ссылки в `trades`:

```sql
DELETE FROM instruments WHERE instrument_id = 1;
```

Ошибка:

```text
Runtime error: FOREIGN KEY constraint failed
```

SQLite отказался удалять SBER, потому что в `trades` всё ещё есть сделки, ссылающиеся на
`instrument_id = 1`. Если бы удаление прошло — эти сделки остались бы ссылаться на
несуществующий инструмент ("сироты" — строки-ссылки в никуда), и мы вернулись бы к той самой
проблеме неоднозначности, с которой начинался этот урок.

### ON DELETE RESTRICT и ON DELETE CASCADE — коротко

То поведение, которое вы только что увидели (отказ в удалении, если есть зависимые строки),
по смыслу соответствует `ON DELETE RESTRICT`. Существует и другой вариант —
`ON DELETE CASCADE`: при удалении родительской строки (инструмента) автоматически удаляются
и все зависимые строки (все сделки по этому инструменту).

**`CASCADE` — это не "универсально хорошее" решение.** Для финансовых данных массовое
автоматическое удаление истории сделок при удалении инструмента из справочника чаще всего
**нежелательно** — так можно случайно стереть реальную историю операций одним неосторожным
`DELETE`. Мы сознательно не используем `CASCADE` в этом курсе. Выбор между `RESTRICT` и
`CASCADE` — это решение о бизнес-смысле данных, а не просто синтаксическая настройка.

## 14. ALTER TABLE и DROP TABLE

`ALTER TABLE` мы уже использовали (добавили колонку `commission`). Посмотрим на
`DROP TABLE` — создадим ненужную тестовую таблицу и удалим её:

```sql
CREATE TABLE scratch_test (x INTEGER);

.tables

DROP TABLE scratch_test;

.tables
```

Таблица `scratch_test` пропала из списка полностью.

### DELETE FROM ... против DROP TABLE ...  — принципиальная разница

```sql
DELETE FROM trades WHERE trade_id = 5;
```

— удаляет **данные** (строки), но сама таблица `trades`, её структура, ограничения и
индексы остаются на месте.

```sql
DROP TABLE trades;
```

— (не выполняйте это по-настоящему, если хотите продолжать урок дальше!) удаляет **саму
таблицу целиком**: и данные, и структуру, и все ограничения. После `DROP TABLE trades;`
таблицы `trades` в базе больше не существует вообще, как будто её никогда не создавали.

Правило простое: `DELETE` — про содержимое, `DROP` — про существование объекта.

## 15. Почему не одна большая таблица (нормализация на пальцах)

Представьте, что вместо `instruments`, `accounts` и `trades` мы бы хранили всё в одной
гигантской таблице:

```text
trade_id | ticker | instrument_name | account_name      | side | quantity | price
---------|--------|------------------|--------------------|------|----------|------
1        | SBER   | Сбербанк         | ACC-EQUITY-CORE    | BUY  | 10       | 280.5
2        | SBER   | Сбербанк         | ACC-EQUITY-CORE    | SELL | 5        | 282.0
3        | SBER   | Сбербанк         | ACC-INTRADAY       | BUY  | 20       | 281.0
...
```

На первый взгляд просто и понятно. Но у такой таблицы есть реальные проблемы:

1. **Дублирование.** Текст `"Сбербанк"` повторяется в сотнях строк. Если по SBER пройдёт
   100 сделок — название "Сбербанк" будет физически записано на диске 100 раз.
2. **Разные написания одного и того же.** Где-то `"Сбербанк"`, где-то по опечатке
   `"Сбербанк "` (с пробелом в конце) или `"сбербанк"` (с маленькой буквы). Для человека это
   один и тот же инструмент, а для базы данных — это просто разные строки текста, ничего не
   связывающие их автоматически.
3. **Аномалия обновления.** Если у Сбербанка в реальности изменится официальное название —
   нужно найти и исправить его **во всех сотнях строк**. Если пропустить хотя бы одну — в
   базе возникнет противоречие: один и тот же инструмент называется по-разному в разных
   местах.
4. **Сложность контроля качества.** Невозможно легко проверить "а все ли тикеры вообще
   существуют и написаны правильно" — нет единого места, где перечислены все допустимые
   инструменты.

### Решение: разделить на связанные таблицы

Именно поэтому мы храним:

- `instruments` — единственное место, где хранится название и характеристики каждого
  инструмента, ровно один раз на инструмент;
- `accounts` — единственное место с описанием счетов;
- `trades` — только сами факты сделок, со ссылками (`instrument_id`, `account_id`) на
  соответствующие справочники.

Если название Сбербанка изменится — вы правите **одну строку** в `instruments`, и это
мгновенно "видно" из всех сделок, которые на неё ссылаются. Это и есть базовая идея
**нормализации**: каждый факт хранится один раз, в одном месте, а связи между фактами
выражаются через ключи, а не через повторение текста.

Мы не будем подробно разбирать формальные "нормальные формы" (1NF, 2NF, 3NF...) — для
уровня этого курса важно именно это интуитивное понимание: *справочник отдельно, факты
отдельно, связь — через ID.*

## 16. Составные ключи (composite keys)

Разберём это на примере дневных цен. У готовой таблицы `daily_prices` в главной базе
первичный ключ составной: `PRIMARY KEY (price_date, instrument_id)`. Соберём маленькую
копию этой идеи здесь:

```sql
CREATE TABLE daily_prices_demo (
    price_date    TEXT NOT NULL,
    instrument_id INTEGER NOT NULL,
    close_price   REAL NOT NULL,

    PRIMARY KEY (price_date, instrument_id),
    FOREIGN KEY (instrument_id) REFERENCES instruments(instrument_id)
);

INSERT INTO daily_prices_demo VALUES ('2024-01-09', 2, 130.00);
INSERT INTO daily_prices_demo VALUES ('2024-01-09', 3, 7100.00);

SELECT * FROM daily_prices_demo;
```

Обе строки вставились нормально — потому что `price_date` сама по себе не уникальна (за
`'2024-01-09'` может быть несколько инструментов), `instrument_id` сама по себе тоже не
уникальна (у одного инструмента много дат), но **пара** (дата + инструмент) не должна
повторяться: у одного инструмента не может быть двух разных цен закрытия в один и тот же
день.

Проверим это:

```sql
INSERT INTO daily_prices_demo VALUES ('2024-01-09', 2, 131.50);
```

Ошибка:

```text
Runtime error: UNIQUE constraint failed: daily_prices_demo.price_date, daily_prices_demo.instrument_id
```

Мы попытались записать вторую цену закрытия GAZP (`instrument_id = 2`) за то же
`'2024-01-09'` — и составной первичный ключ это запретил, ровно как и было задумано.

## 17. Индексы — самое базовое представление

Это только вводное знакомство — тема производительности подробно будет позже в курсе.

- **Ключ** (`PRIMARY KEY`, `UNIQUE`) — это **правило**, ограничение на то, какие данные
  допустимы.
- **Индекс** — это отдельная вспомогательная структура, которая помогает SQLite **быстрее
  находить** нужные строки, не просматривая таблицу целиком.

Ключ и индекс — не одно и то же, но часто связаны: когда вы объявляете `PRIMARY KEY` или
`UNIQUE`, SQLite обычно автоматически создаёт индекс, чтобы быстро проверять уникальность.
Посмотрите на это своими глазами:

```sql
PRAGMA index_list('instruments');
```

Вы увидите автоматически созданный индекс для ограничения `UNIQUE` на колонке `ticker`
(индекс для самого `PRIMARY KEY` отдельно может не отображаться здесь, если это
`INTEGER PRIMARY KEY` — потому что тогда, как мы уже знаем, он и есть `rowid`, а не
отдельный индекс).

```sql
PRAGMA index_list('daily_prices_demo');
```

Здесь вы увидите индекс, обслуживающий составной `PRIMARY KEY (price_date, instrument_id)`.

Запомните на будущее: если запрос по большой таблице работает медленно, часто (не всегда)
решение — это добавить подходящий индекс. Подробно про `CREATE INDEX` и то, как выбирать,
какие индексы нужны, поговорим отдельно позже в курсе (см. `LEARNING_PATH.md`).
