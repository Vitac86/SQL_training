## 3. INNER JOIN по шагам

Задача: вывести сделки вместе с тикером инструмента, а не только числовым `instrument_id`.

```sql
SELECT
    t.trade_id,
    t.trade_date,
    i.ticker,
    t.side,
    t.quantity,
    t.price
FROM trades AS t
JOIN instruments AS i
    ON i.instrument_id = t.instrument_id
LIMIT 10;
```

Разберём этот запрос буквально по частям:

- `FROM trades AS t` — берём таблицу `trades` и даём ей короткий псевдоним `t`, чтобы не
  писать полное имя `trades` перед каждой колонкой.
- `JOIN instruments AS i` — присоединяем таблицу `instruments` с псевдонимом `i`. Без
  уточнения `JOIN` в SQLite означает `INNER JOIN` — это один и тот же оператор, просто слово
  `INNER` необязательно писать явно.
- `ON i.instrument_id = t.instrument_id` — это **условие соединения**. Читайте его буквально:
  *для каждой строки сделки найди подходящую строку инструмента с таким же идентификатором.*
  SQLite проходит по строкам `trades` одну за другой и для каждой ищет в `instruments`
  строку, где `instrument_id` совпадает.
- В `SELECT` мы теперь можем обращаться к колонкам обеих таблиц одновременно: `t.trade_id`,
  `t.side` — из `trades`, `i.ticker` — из `instruments`.

### Что физически происходит со строками

```text
строка trades
      +
совпавшая строка instruments
      =
одна более широкая результирующая строка
```

**Важное правило INNER JOIN**: если для строки `trades` совпадение по `ON` не нашлось — такой
строки в результате `INNER JOIN` **не будет вообще**. `INNER JOIN` показывает только те пары
строк, где совпадение реально нашлось в обеих таблицах.

### Граница между FOREIGN KEY и JOIN

Эти два понятия легко перепутать, поэтому явно зафиксируем разницу ещё раз, теперь уже глядя
на настоящий `JOIN`:

```text
FOREIGN KEY
контролирует допустимость ссылки
(не даёт записать сделку на несуществующий instrument_id — это вы проверяли
через PRAGMA foreign_key_list('trades') в уроке 1)

JOIN
получает связанные данные
(достаёт ticker для уже существующей сделки — прямо сейчас, в этом запросе)
```

`FOREIGN KEY` работает только в момент записи (`INSERT`/`UPDATE`) и не имеет отношения к тому,
что показывает `SELECT`. Именно поэтому в уроке 1 `SELECT * FROM trades;` показывал только
`instrument_id`, а не `ticker`, хотя `FOREIGN KEY` на `instruments` в схеме объявлен. `JOIN`,
наоборот, ничего не проверяет и не запрещает — он только ищет совпадения и подставляет данные
рядом.

## 4. Соединяем сразу три таблицы

```sql
SELECT
    t.trade_id,
    t.trade_date,
    a.account_name,
    i.ticker,
    t.side,
    t.quantity,
    t.price,
    t.quantity * t.price AS turnover
FROM trades AS t
JOIN instruments AS i ON i.instrument_id = t.instrument_id
JOIN accounts    AS a ON a.account_id    = t.account_id
ORDER BY t.trade_date
LIMIT 10;
```

`JOIN` можно "цеплять" один за другим сколько угодно раз — каждый добавляет ещё одну таблицу,
у каждой свой `ON` со своим условием совпадения.

Проверим на той самой сделке, которую вы разбирали в уроке 1 вручную:

```sql
SELECT
    t.trade_id,
    i.ticker,
    a.account_name,
    t.side
FROM trades AS t
JOIN instruments AS i ON i.instrument_id = t.instrument_id
JOIN accounts    AS a ON a.account_id    = t.account_id
WHERE t.trade_id = 1;
```

Результат: `ticker = 'LKOH'`, `account_name = 'ACC-FIXEDINCOME'`, `side = 'SELL'` — ровно то
же самое, что вы нашли вручную в уроке 1, только теперь одной командой вместо трёх отдельных
`SELECT`.

## 5. LEFT JOIN: инструмент без сделок

Вспомните урок 1 — инструмент `TEST0` не имеет ни одной сделки. Проверим это через
`INNER JOIN`:

```sql
SELECT i.ticker, t.trade_id
FROM instruments AS i
JOIN trades AS t ON t.instrument_id = i.instrument_id
WHERE i.ticker = 'TEST0';
```

Результат — **пустой**. `TEST0` просто не появляется в результате `INNER JOIN`, потому что
для него нет ни одной подходящей строки в `trades` — а `INNER JOIN` показывает только те
строки, где совпадение реально нашлось.

Теперь то же самое через `LEFT JOIN`:

```sql
SELECT i.ticker, t.trade_id
FROM instruments AS i
LEFT JOIN trades AS t ON t.instrument_id = i.instrument_id
WHERE i.ticker = 'TEST0';
```

Результат — одна строка: `TEST0` и `trade_id = NULL`. `LEFT JOIN` (по-другому — `LEFT OUTER
JOIN`, слово `OUTER` необязательно) означает: **оставить все строки из "левой" таблицы** (той,
что указана в `FROM`, — здесь `instruments`), даже если для них не нашлось ни одной подходящей
строки в "правой" таблице (`trades`). Там, где совпадения нет, колонки правой таблицы просто
заполняются `NULL`.

Найдём **все** инструменты без единой сделки одним запросом:

```sql
SELECT i.instrument_id, i.ticker
FROM instruments AS i
LEFT JOIN trades AS t ON t.instrument_id = i.instrument_id
WHERE t.trade_id IS NULL;
```

Смысл: "возьми все инструменты, присоедини к ним сделки (если есть), и оставь только те, у
кого после присоединения `trade_id` оказался пустым" — то есть ни одной сделки не нашлось.

## 6. LEFT JOIN: счёт без сделок

Ровно та же логика применима к `accounts` — вспомните `'ACC-DORMANT'` из урока 1:

```sql
SELECT a.account_id, a.account_name
FROM accounts AS a
LEFT JOIN trades AS t ON t.account_id = a.account_id

```

Это вернёт `'ACC-DORMANT'` — счёт, который существует в справочнике `accounts`, но ни разу не
участвовал в сделках.

## 7. INNER JOIN против LEFT JOIN — итоговое правило

| | Что делает |
|---|---|
| `INNER JOIN` | Оставляет только строки, у которых нашлось совпадение **в обеих** таблицах |
| `LEFT JOIN` | Оставляет **все** строки левой таблицы; если совпадения нет — колонки правой таблицы заполняются `NULL` |

Если бы мы построили отчёт "оборот по каждому инструменту" через `INNER JOIN`, `TEST0` в нём
вообще не появился бы — как будто такого инструмента не существует. Для отчёта "покажи вообще
все инструменты, включая те, по которым ещё не было ни одной сделки" обязательно нужен
`LEFT JOIN`.

## 8. Ловушка: COUNT(*) против COUNT(t.trade_id)

Построим отчёт: для каждого счёта — сколько у него сделок. Естественно взять `LEFT JOIN` — мы
же хотим видеть в отчёте и `'ACC-DORMANT'`, у которого сделок нет вообще:

```sql
SELECT
    a.account_name,
    COUNT(*) AS trades_count
FROM accounts AS a
LEFT JOIN trades AS t ON t.account_id = a.account_id
GROUP BY a.account_name;
```

Посмотрите на строку `'ACC-DORMANT'` в результате — там `trades_count = 1`. Это **неверно**: у
`'ACC-DORMANT'` ноль сделок, мы это проверяли и в уроке 1, и разделом выше. Что произошло:
`LEFT JOIN` для `'ACC-DORMANT'` всё равно создал ровно одну строку результата (саму строку
счёта, "дополненную" пустыми `NULL` вместо колонок `trades`), а `COUNT(*)` честно посчитал эту
одну строку целиком — не заглядывая внутрь, есть там реальная сделка или один сплошной `NULL`.

Правильный вариант — считать не строки целиком, а конкретную колонку из `trades`:

```sql
SELECT
    a.account_name,
    COUNT(t.trade_id) AS trades_count
FROM accounts AS a
LEFT JOIN trades AS t ON t.account_id = a.account_id
GROUP BY a.account_name;
```

Теперь `'ACC-DORMANT'` показывает `trades_count = 0`. Причина: `COUNT(колонка)`, в отличие от
`COUNT(*)`, считает только **не-NULL** значения именно этой колонки. У `'ACC-DORMANT'` после
`LEFT JOIN` значение `t.trade_id` — это в точности `NULL` (реальной сделки нет), и `COUNT` его
корректно не засчитывает.

Правило на будущее: после `LEFT JOIN`, если считаете `COUNT`, почти всегда нужен именно
`COUNT(колонка_из_правой_таблицы)`, а не `COUNT(*)` — если только вы осознанно не хотите
считать сами результирующие строки, включая "пустые".

## 9. Ловушка: WHERE после LEFT JOIN

Ещё одна классическая ошибка. Попробуем получить список счетов вместе с их BUY-сделками:

```sql
SELECT
    a.account_name,
    t.trade_id,
    t.side
FROM accounts AS a
LEFT JOIN trades AS t ON t.account_id = a.account_id
WHERE t.side = 'BUY';
```

Проверьте: есть ли в результате `'ACC-DORMANT'`? Его там **нет** — хотя мы явно написали
`LEFT JOIN`, который по определению должен был сохранить все строки `accounts`.

Что произошло: `LEFT JOIN` действительно сначала честно создал строку для `'ACC-DORMANT'` — со
значением `t.side = NULL` (реальной сделки нет, подставить нечего). Но затем сработал
`WHERE t.side = 'BUY'` — а `NULL = 'BUY'` **никогда** не является истиной, даже для настоящих
`NULL`-значений. Строка `'ACC-DORMANT'` не прошла условие `WHERE` и была отфильтрована — ровно
так же, как если бы вы с самого начала использовали `INNER JOIN`.

Сравните два запроса напрямую. Без `WHERE`, сгруппированный по счёту:

```sql
SELECT
    a.account_name,
    COUNT(t.trade_id) AS trades_count
FROM accounts AS a
LEFT JOIN trades AS t ON t.account_id = a.account_id
GROUP BY a.account_name;
```

— 6 строк, включая `'ACC-DORMANT'` с `trades_count = 0`. Теперь с `WHERE t.side = 'BUY'` перед
`GROUP BY`:

```sql
SELECT
    a.account_name,
    COUNT(t.trade_id) AS trades_count
FROM accounts AS a
LEFT JOIN trades AS t ON t.account_id = a.account_id
WHERE t.side = 'BUY'
GROUP BY a.account_name;
```

— уже 5 строк: `'ACC-DORMANT'` пропал полностью, а не показал `0`.

Вывод: `LEFT JOIN` сохраняет "пустые" строки только до тех пор, пока их не отфильтрует
последующий `WHERE` по колонке из присоединённой (правой) таблицы. Это тонкое место, в котором
синтаксически полностью правильный SQL тихо даёт финансово неверный отчёт — без единой ошибки
или предупреждения от SQLite. (Если бы нужно было оставить именно BUY-сделки, но не потерять
`'ACC-DORMANT'` — условие на `side` переносят из `WHERE` в сам `ON`: `LEFT JOIN trades AS t ON
t.account_id = a.account_id AND t.side = 'BUY'`. Это уже нюанс за рамками этого урока, но
полезно знать, что выход есть.)

## 10. JOIN по нескольким колонкам

До сих пор мы всегда соединяли таблицы по одному совпадению — `instrument_id`. Но не любая
пара таблиц связана только одной колонкой. Попробуем соединить `trades` с `daily_prices`,
чтобы рядом со сделкой видеть цену закрытия того же дня:

```sql
SELECT
    t.trade_id,
    t.trade_date,
    t.instrument_id,
    p.close_price
FROM trades AS t
JOIN daily_prices AS p
    ON p.instrument_id = t.instrument_id
WHERE t.trade_id = 17;
```

Выполните и посмотрите на количество строк в Query Results — их **39**, хотя сделка
`trade_id = 17` ровно одна! Причина: в `daily_prices` на один `instrument_id` приходится 39
разных дневных цен (39 разных `price_date` — по одной на каждый день периода наблюдений).
Условие `ON p.instrument_id = t.instrument_id` говорит только "тот же инструмент" — и ему
**одинаково подходят все 39 строк** `daily_prices` этого инструмента, потому что ничем другим
для `ON` они не отличаются. Одна сделка "размножилась" на 39 строк результата — это называется
**fan-out** (разрастание результата за счёт неполного условия соединения).

Проблема в том, что "тот же инструмент" — это не то же самое, что "та же цена на ту же дату".
Добавим второе условие прямо в `ON`:

```sql
SELECT
    t.trade_id,
    t.trade_date,
    t.instrument_id,
    p.close_price
FROM trades AS t
JOIN daily_prices AS p
    ON p.instrument_id = t.instrument_id
   AND p.price_date    = t.trade_date
WHERE t.trade_id = 17;
```

Теперь строка ровно одна — цена закрытия именно на дату сделки. `AND` внутри `ON` работает
так же, как `AND` в `WHERE`: обе части должны быть истинны одновременно для конкретной пары
строк, чтобы SQLite посчитал их совпадением.

Вывод, который стоит запомнить: `ON` — это буквально то условие, которое вы в нём написали, ни
байтом больше. SQLite не «додумывает» за вас, что вы наверняка имели в виду ещё и совпадение по
дате — если написан только `instrument_id = instrument_id`, соединение пройдёт только по
инструменту, со всеми лишними строками. `ON` — это условие сопоставления, которое вы
формулируете сами под конкретную задачу, а не какой-то автоматически подразумеваемый «ключ».

## 11. Коротко: RIGHT JOIN и FULL OUTER JOIN

`RIGHT JOIN` — зеркальная противоположность `LEFT JOIN`: сохраняет все строки **правой**
таблицы. `FULL OUTER JOIN` — сохраняет все строки **обеих** таблиц одновременно, заполняя
`NULL` там, где совпадения нет ни с одной из сторон.

Оба варианта реально проверены на установленной в этом проекте версии SQLite (`3.53.4`) — оба
работают:

```sql
SELECT a.account_id, t.trade_id
FROM trades AS t
RIGHT JOIN accounts AS a ON a.account_id = t.account_id
WHERE t.trade_id IS NULL;
```

Этот `RIGHT JOIN` находит того же самого `'ACC-DORMANT'`, что и `LEFT JOIN` из раздела выше —
просто таблицы в `FROM`/`JOIN` поменяны местами. На практике `RIGHT JOIN` почти не используют —
почти любой `RIGHT JOIN` можно переписать как `LEFT JOIN`, просто поменяв таблицы местами, а
это привычнее читать. Подробно эти два варианта в этом курсе не разбираются — этого краткого
знакомства достаточно, чтобы не растеряться, встретив их в чужом коде.
