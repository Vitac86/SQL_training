# Урок 17. Кто имеет право читать и изменять базу

**Знакомо:** база, таблицы, SELECT/UPDATE, SSMS. **Новое:** пользователь SQL Server, login, роль и разрешения.

## 1. Не все сотрудники должны делать одно и то же

Представь три функции:
- Аналитик смотрит сделки, строит отчёты, **не меняет** записи.
- Оператор может записывать определённые сделки, но не управлять сервером.
- Администратор устанавливает сервер, управляет правами и резервными копиями.

Выдать всем полный доступ — это как дать каждому сотруднику ключи от сейфа и серверной. Работать возможно, но очень рискованно. Поэтому используют **принцип минимально необходимых прав**.

## 2. Два близких понятия: login и user

Когда ты подключился из SSMS через Windows Authentication, SQL Server установил, **кто обращается**.

- **Login** — учётная запись для входа **на экземпляр SQL Server**.
- **User** — учётная запись **в конкретной базе** (`TradingTraining`), которой назначают права внутри БД.

Одна и та же учётная запись может иметь доступ к одной базе и не иметь к другой. Важна связка login → user/права.

Проверим свой сеанс (без изменений):

```sql
USE TradingTraining;

SELECT ORIGINAL_LOGIN() AS login_name,
       USER_NAME() AS database_user;
```

Сравни значения и объясни: первое отвечает на вопрос «под кем подключился», второе — «кем считаюсь внутри этой базы».

## 3. Роли: набор прав

**Role / роль** — удобная «группа полномочий». Например, роль `report_reader` может иметь право `SELECT` определённых таблиц.

Слова, которые ты встретишь в администрировании:

- `GRANT` — разрешить действие.
- `REVOKE` — убрать ранее заданное явное разрешение/запрет.
- `DENY` — явно запретить (с оговорками о приоритетах и владении).

Профессиональная тема — **наследование полномочий**, а не просто три команды; сейчас достаточно понимать назначение.

## 4. Посмотреть, что задано в SSMS

В Object Explorer раскрой `TradingTraining → Security / Безопасность → Users / Пользователи` и `Roles / Роли`. **Ничего не удаляй и не переназначай** — пока только посмотри.

В папке **Security / Безопасность** самого сервера находятся **Logins / Имена входа**. Теперь различие «права на сервер» и «права внутри базы» видно не только по определению, но и в интерфейсе.

## 5. Пример выдачи прав — только для чтения кода

Следующий текст **не надо запускать**, пока у тебя нет отдельного созданного учебного пользователя и понимания, кому даются права:

```sql
-- CREATE ROLE report_reader;
-- GRANT SELECT ON dbo.trades TO report_reader;
-- ALTER ROLE report_reader ADD MEMBER [existing_database_user];
```

Смысл:
1. Создать роль.
2. Разрешить роли читать таблицу.
3. Назначить роль конкретному пользователю.

В реальных системах используют отдельные роли и иногда представления, ограничивающие видимую информацию. **Наличие SQL-доступа не означает, что пользователь вправе видеть всех клиентов** — эту бизнес-логику нужно проектировать специально.

## 6. Почему приложениям нельзя давать sysadmin

Роль `sysadmin` имеет практически полный контроль над экземпляром SQL Server. Для приложения, которое лишь записывает поручения, это чрезмерно: ошибка в приложении может получить слишком большие последствия.

Поэтому предпочитают давать права на конкретные операции и проверять входные значения, а не собирать SQL текстовой конкатенацией. Иначе появляется риск **SQL-инъекции**: пользовательский текст может изменить смысл команды. Значения из приложений передают **параметрами**, а не склеивают SQL-строки.

## Задания

1. Выполни запрос `ORIGINAL_LOGIN()` и `USER_NAME()`.
2. Найди папки Logins и Users в SSMS и объясни, почему они находятся на разных уровнях.
3. Придумай минимальные права для аналитика, оператора и администратора.
4. Чем отличается `GRANT SELECT` от `GRANT UPDATE`?

**Самопроверка:** имя входа относится к серверу, пользователь — к базе, права определяют допустимые действия; кому нужен только SELECT, не стоит выдавать UPDATE/DELETE.
