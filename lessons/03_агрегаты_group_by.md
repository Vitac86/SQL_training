## 2. Агрегатные функции без GROUP BY

Агрегатная функция превращает **много строк в одно число**.

```sql
SELECT COUNT(*) FROM trades;

SELECT SUM(quantity * price) AS total_turnover FROM trades;

SELECT AVG(price) AS avg_price FROM trades;

SELECT MIN(price) AS min_price, MAX(price) AS max_price FROM trades;
```

- `COUNT(*)` — сколько всего строк (сделок). Реально вернёт `230` — столько строк в `trades`,
  как вы уже знаете из урока 1.
- `SUM(...)` — сумма значений (общий оборот). Реально вернёт около `108 276 564.54`.
- `AVG(...)` — среднее значение. Реально вернёт около `773.55`.
- `MIN(...)` / `MAX(...)` — минимум и максимум. Реально вернёт `12.49` и `7764.84`.

Без `GROUP BY` агрегат считается **по всей таблице целиком** — вы получаете ровно одну строку
результата, независимо от того, сколько строк было в таблице до этого.

## 3. GROUP BY — тот же агрегат, но по группам

Реальный вопрос трейдера обычно звучит не "сколько всего сделок", а "сколько сделок **по
каждому инструменту**" или "**по каждой стороне**". Вот тут и нужен `GROUP BY`:

```sql
SELECT
    side,
    COUNT(*) AS trades_count
FROM trades
GROUP BY side;
```

Как это работает: SQLite сначала мысленно "раскладывает" все строки `trades` по стопкам — в
одной стопке все строки с `side = 'BUY'`, в другой — все с `side = 'SELL'`. Затем `COUNT(*)`
считается **отдельно для каждой стопки**, а не для таблицы целиком:

```text
230 сделок
      ↓
GROUP BY side
      ↓
BUY:  110 строк → одна результирующая строка
SELL: 120 строк → одна результирующая строка
```

Из 230 строк получились ровно 2 строки результата — по одной на каждое встретившееся значение
`side`.

То же самое, но по инструменту, и сразу с оборотом:

```sql
SELECT
    instrument_id,
    COUNT(*) AS trades_count,
    SUM(quantity * price) AS turnover
FROM trades
GROUP BY instrument_id
ORDER BY turnover DESC;
```

Оборот по каждому счёту:

```sql
SELECT
    account_id,
    SUM(quantity * price) AS turnover,
    SUM(commission) AS commission_total
FROM trades
GROUP BY account_id
ORDER BY turnover DESC;
```

Обратите внимание: колонка `account_id` показывает только число, а не название счёта — мы ещё
не соединили `trades` со справочником `accounts`. Это сделаем в уроке 4 через `JOIN`. Здесь
важно другое: сам механизм группировки уже работает и без `JOIN`.

### Правило, которое часто ломает новичков

В `SELECT` вместе с `GROUP BY` можно указывать **только** те колонки, по которым группируем, и
агрегатные функции. Так работать нельзя по смыслу:

```sql
SELECT instrument_id, price FROM trades GROUP BY instrument_id;
```

SQLite (в отличие от некоторых строгих СУБД) не всегда выдаст здесь явную ошибку, но результат
будет **непредсказуемым** — какая именно `price` попадёт в строку, если инструменту
соответствует 20 разных сделок с разными ценами? Правильный вопрос — не "какая цена", а какая
**сумма/среднее/минимум** цен. Формулируйте вопрос через агрегатную функцию явно: `AVG(price)`,
`MIN(price)`, `MAX(price)`.

## 4. WHERE фильтрует до группировки, HAVING — после

Это одно из главных мест урока. Модель такая:

```text
WHERE
фильтрует строки
ДО группировки

GROUP BY
создаёт группы

HAVING
фильтрует уже готовые группы
ПОСЛЕ группировки
```

Разница на практике — это разные вопросы. Сначала вопрос вида "сколько BUY-сделок по каждому
счёту" — здесь `WHERE` убирает лишние строки **до** того, как они попадут в группы:

```sql
SELECT
    account_id,
    COUNT(*) AS trades_count
FROM trades
WHERE side = 'BUY'
GROUP BY account_id;
```

Реальный результат — 5 строк (счёт `6` / `ACC-DORMANT` отсутствует, у него вообще нет сделок,
ни BUY, ни SELL):

| account_id | trades_count (только BUY) |
|---|---|
| 5 | 31 |
| 1 | 22 |
| 2 | 21 |
| 4 | 18 |
| 3 | 18 |

Теперь другой вопрос: "у каких счетов **вообще** (BUY и SELL вместе) больше 45 сделок" — это
вопрос уже к готовым группам, отвечает на него `HAVING`:

```sql
SELECT
    account_id,
    COUNT(*) AS trades_count
FROM trades
GROUP BY account_id
HAVING COUNT(*) > 45;
```

Реальный результат — 3 строки из 5 (счета с `trades_count` `52`, `51`, `47` проходят порог;
`43` и `37` — нет):

| account_id | trades_count (все сделки) |
|---|---|
| 5 | 52 |
| 1 | 51 |
| 4 | 47 |

Написать `WHERE COUNT(*) > 45` вместо `HAVING` **нельзя** — на момент вычисления `WHERE`
агрегат `COUNT(*)` ещё не существует, он появляется только после группировки. `WHERE` в
принципе не видит результатов агрегатных функций — только исходные колонки строк.

## 5. AVG(price) — это не средневзвешенная цена

Важное финансовое предостережение. `AVG(price)` считает **простое** среднее: складывает цену
каждой сделки и делит на количество сделок, никак не учитывая, сколько бумаг было куплено или
продано в каждой из них. Проверим на реальных данных, на инструменте `LKOH`
(`instrument_id = 3`):

```sql
SELECT
    ROUND(AVG(price), 2) AS simple_avg_price,
    ROUND(SUM(quantity * price) / SUM(quantity), 2) AS weighted_avg_price
FROM trades
WHERE instrument_id = 3;
```

Реальный результат: `simple_avg_price = 7302.88`, а `weighted_avg_price = 7242.79` — два
заметно разных числа, хотя оба честно описывают "среднюю цену LKOH".

Разница в том, что именно каждое число отвечает:

- `AVG(price)` — "если взять все сделки и посчитать по ним простое среднее цены, не глядя на
  объём" — сделка на 1 бумагу и сделка на 20 бумаг влияют на результат **одинаково**.
- `SUM(quantity * price) / SUM(quantity)` — "сколько в среднем стоила одна бумага, если
  учитывать, что при более крупных сделках эта цена действовала на большее количество бумаг" —
  это и есть **средневзвешенная цена** (взвешенная по объёму).

Для реальных финансовых выводов ("по какой цене мы в среднем покупали/продавали этот
инструмент") обычно нужна именно средневзвешенная цена, а не простое `AVG`.

Отдельно — важная граница применимости этой формулы: она осмысленна только **внутри одного
инструмента** (или однородной группы). Не пытайтесь наивно посчитать
`SUM(quantity * price) / SUM(quantity)` сразу по всей таблице `trades` без `GROUP BY
instrument_id` — у `RUSFAR` количество в сделке измеряется сотнями тысяч, а у `LKOH` —
единицами-десятками; сложенные вместе такие `quantity` физически не сопоставимы и результат не
будет иметь экономического смысла, несмотря на синтаксически корректный SQL.

## 6. CASE — условная логика внутри запроса

`CASE` — это выражение, которое сначала стоит понять **для одной строки**, и только потом — в
сочетании с агрегатом.

```sql
SELECT
    trade_id,
    side,
    quantity,
    CASE
        WHEN side = 'BUY' THEN quantity
        WHEN side = 'SELL' THEN -quantity
        ELSE 0
    END AS signed_quantity
FROM trades
LIMIT 10;
```

Здесь `CASE` работает как if/elif/else — но выполняется **отдельно для каждой строки**: для
строки с `side = 'BUY'` он возвращает `quantity` как есть, для `side = 'SELL'` — то же число со
знаком минус. Ни агрегатов, ни `GROUP BY` здесь ещё нет — просто новая вычисляемая колонка,
как `turnover` в уроке 2.

Дальше — знакомая уже идея: если такую вычисленную "для каждой строки" колонку сложить агрегатом
по группе, получится содержательный показатель:

```text
CASE для каждой сделки
          ↓
SUM(...)
          ↓
условная позиция по инструменту
```

```sql
SELECT
    instrument_id,
    SUM(
        CASE
            WHEN side = 'BUY' THEN quantity
            WHEN side = 'SELL' THEN -quantity
            ELSE 0
        END
    ) AS net_position
FROM trades
GROUP BY instrument_id
ORDER BY net_position DESC;
```

Мы превратили `BUY`/`SELL` в положительное/отрицательное число и сложили по каждому
инструменту — классический приём для расчёта **условной позиции**: если сложить
`signed_quantity` по всем сделкам одного инструмента, получится примерная текущая позиция (без
учёта начального остатка, комиссий и прочих тонкостей реального учёта).

Решений здесь нет — они в `lessons/answers/03_answers.md`.

   — можно группировать сразу по нескольким колонкам).
