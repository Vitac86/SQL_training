# Ответы к уроку 20 — эталон итогового проекта

[Вернуться к уроку](../20_итоговый_проект.md) · [Все ответы](README.md)

Это **один учебный вариант реализации**, а не схема готовой брокерской системы. Он позволяет самостоятельно проверить этапы урока 20. Сначала выполни проект без подсказок, а потом сравни с эталоном.

**Безопасность:** все изменения ниже касаются **только новых таблиц** `dbo.lesson20_orders` и `dbo.lesson20_executions` в учебной `TradingTraining`. Таблицы `trades`, `accounts`, `instruments` не меняются. Команды создания и загрузки выполняй поэтапно, **не повторяй INSERT для тех же PK**.

## 1–2. Проект отношений

```text
dbo.accounts       dbo.instruments
 account_id (PK)    instrument_id (PK)
      |                    |
      +--------+-----------+
               |
    lesson20_orders
      order_id (PK)
      account_id (FK)
      instrument_id (FK)
      external_order_id (UNIQUE)
      side, quantity, limit_price, submitted_at, status
               |
               | один заказ → от 0 до многих исполнений
               |
    lesson20_executions
      execution_id (PK)
      order_id (FK)
      executed_at, quantity, price, commission
```

`order_id` живёт в таблице исполнений как внешний ключ: **одному поручению может соответствовать любое допустимое число исполнений**. Поля `execution1`, `execution2` в строке поручения сделали бы структуру негибкой.

## 3. Создать две таблицы

В новом окне SSMS выполни весь фрагмент. Если таблицы уже созданы при самостоятельном решении, **не выполняй CREATE повторно** — сравни свой вариант с эталоном.

```sql
USE TradingTraining;
GO

CREATE TABLE dbo.lesson20_orders (
    order_id INT NOT NULL
        CONSTRAINT PK_lesson20_orders PRIMARY KEY,

    external_order_id VARCHAR(40) NOT NULL
        CONSTRAINT UQ_lesson20_external UNIQUE,

    account_id INT NOT NULL
        CONSTRAINT FK_lesson20_orders_account
        REFERENCES dbo.accounts(account_id),

    instrument_id INT NOT NULL
        CONSTRAINT FK_lesson20_orders_instrument
        REFERENCES dbo.instruments(instrument_id),

    side VARCHAR(4) NOT NULL
        CONSTRAINT CK_lesson20_orders_side
        CHECK (side IN ('BUY', 'SELL')),

    quantity INT NOT NULL
        CONSTRAINT CK_lesson20_orders_qty CHECK (quantity > 0),

    limit_price DECIMAL(19,4) NULL
        CONSTRAINT CK_lesson20_orders_price
        CHECK (limit_price > 0),

    submitted_at DATETIME2(0) NOT NULL,

    status VARCHAR(12) NOT NULL
        CONSTRAINT CK_lesson20_orders_status
        CHECK (status IN ('NEW', 'PARTIAL', 'FILLED', 'CANCELED'))
);
GO

CREATE TABLE dbo.lesson20_executions (
    execution_id INT NOT NULL
        CONSTRAINT PK_lesson20_executions PRIMARY KEY,

    order_id INT NOT NULL
        CONSTRAINT FK_lesson20_exec_order
        REFERENCES dbo.lesson20_orders(order_id),

    executed_at DATETIME2(0) NOT NULL,

    quantity INT NOT NULL
        CONSTRAINT CK_lesson20_exec_qty CHECK (quantity > 0),

    price DECIMAL(19,4) NOT NULL
        CONSTRAINT CK_lesson20_exec_price CHECK (price > 0),

    commission DECIMAL(19,4) NOT NULL
        CONSTRAINT CK_lesson20_exec_commission CHECK (commission >= 0)
);
GO
```

**Почему `limit_price` может быть NULL?** Рыночное поручение может не иметь лимитной цены. Правило `CHECK (limit_price > 0)` не запрещает NULL: когда значение отсутствует, сравнение имеет результат UNKNOWN, а CHECK в SQL Server отклоняет **FALSE**, не UNKNOWN. Поэтому `NULL` здесь допустим, а `0` и отрицательные цены — нет.

## 4. Добавить четыре поручения и три исполнения

**Выполняй только после создания таблиц и только один раз.** Для ссылок используем существующие учебные счета и инструменты.

```sql
INSERT INTO dbo.lesson20_orders
  (order_id, external_order_id, account_id, instrument_id,
   side, quantity, limit_price, submitted_at, status)
VALUES
  (1, 'DEMO-ORDER-001', 1, 1, 'BUY', 100, 300.0000,
     '2024-01-09T10:00:00', 'FILLED'),
  (2, 'DEMO-ORDER-002', 2, 2, 'SELL', 50, 130.0000,
     '2024-01-09T10:05:00', 'NEW'),
  (3, 'DEMO-ORDER-003', 3, 3, 'BUY', 20, 7100.0000,
     '2024-01-09T10:10:00', 'PARTIAL'),
  (4, 'DEMO-ORDER-004', 4, 1, 'BUY', 10, 310.0000,
     '2024-01-09T10:20:00', 'CANCELED');

INSERT INTO dbo.lesson20_executions
  (execution_id, order_id, executed_at, quantity, price, commission)
VALUES
  (1, 1, '2024-01-09T10:01:00', 40, 299.5000, 1.20),
  (2, 1, '2024-01-09T10:02:00', 60, 299.8000, 1.80),
  (3, 3, '2024-01-09T10:11:00', 5, 7090.0000, 2.50);

SELECT COUNT(*) AS orders_count FROM dbo.lesson20_orders;

```

Ожидается **4 поручения и 3 исполнения**. Для `order_id=1` два исполнения, для `3` одно, для `2` и `4` ноль.

## 5. Отчёт №1: поручения с тикером и счётом

```sql
SELECT o.order_id, a.account_name, i.ticker,
       o.side, o.quantity, o.status
FROM dbo.lesson20_orders AS o
JOIN dbo.accounts AS a ON a.account_id = o.account_id
JOIN dbo.instruments AS i ON i.instrument_id = o.instrument_id
ORDER BY o.order_id;
```

Результат — **4 строки**, одна на поручение. Мы **не соединяем executions**, поэтому частичные исполнения не размножают строки отчёта.

## 6. Отчёт №2: исполнено и осталось

```sql
SELECT
    o.order_id,
    o.quantity AS ordered_qty,
    COALESCE(SUM(e.quantity), 0) AS filled_qty,
    o.quantity - COALESCE(SUM(e.quantity), 0) AS remaining_qty
FROM dbo.lesson20_orders AS o
LEFT JOIN dbo.lesson20_executions AS e
    ON e.order_id = o.order_id
GROUP BY o.order_id, o.quantity
ORDER BY o.order_id;
```

Ожидается:

```text
order_id  ordered_qty  filled_qty  remaining_qty
1         100          100          0
2          50            0         50
3          20            5         15
4          10            0         10
```

Почему `LEFT JOIN`? Без него поручения 2 и 4 **исчезли бы**, ведь исполнений у них нет. Почему `COALESCE`? `SUM` без подходящих значений даёт NULL, но «фактически исполнено» в данном контексте равно 0.

## 7. Отчёт №3: VWAP и комиссия по каждому поручению

```sql
SELECT
    o.order_id,
    COUNT(e.execution_id) AS execution_count,
    COALESCE(SUM(e.commission), 0) AS commission_total,
    SUM(CAST(e.quantity AS DECIMAL(19,4)) * e.price)
      / NULLIF(SUM(CAST(e.quantity AS DECIMAL(19,4))), 0)
      AS execution_vwap
FROM dbo.lesson20_orders AS o
LEFT JOIN dbo.lesson20_executions AS e
    ON e.order_id = o.order_id
GROUP BY o.order_id
ORDER BY o.order_id;
```

Для `order_id=1`: `(40*299.5 + 60*299.8) / 100 = 299.68`. Для `order_id=3`: **7090.00**. Для поручений **2 и 4** исполнений нет, поэтому `execution_vwap = NULL`, а не 0. Это принципиально: отсутствие исполнения не означает нулевую рыночную цену.

## 8. Проверяем бизнес-противоречия

```sql
WITH fills AS (
    SELECT order_id, SUM(quantity) AS filled_qty
    FROM dbo.lesson20_executions
    GROUP BY order_id
)
SELECT o.order_id, o.status, o.quantity,
       COALESCE(f.filled_qty, 0) AS filled_qty
FROM dbo.lesson20_orders AS o
LEFT JOIN fills AS f ON f.order_id = o.order_id
WHERE COALESCE(f.filled_qty, 0) > o.quantity
   OR (o.status = 'FILLED'
       AND COALESCE(f.filled_qty, 0) <> o.quantity)
   OR (o.status = 'NEW'
       AND COALESCE(f.filled_qty, 0) > 0);
```

Для исходных тестовых данных ожидается **0 строк** — явных противоречий нет. Это пример **контроля**, а не полного промышленного автомата статусов.

Ошибочные `quantity <= 0`, `price <= 0`, повторные `external_order_id` и ссылка на несуществующий `order_id` должны быть отклонены уже **CHECK / UNIQUE / FOREIGN KEY** при записи.

## 9. Двойное исполнение: почему одних FK и CHECK мало

Допустим, у поручения осталось **20**. Два обработчика одновременно проверяют остаток и оба хотят исполнить по **15**. Отдельные новые исполнения проходят `CHECK (quantity > 0)` и FK, но **в сумме получается 30**, что превышает остаток.

Для промышленного решения требуется **атомарное резервирование** оставшегося количества в транзакции (например, защищённый условный UPDATE строки поручения с проверкой числа затронутых строк) и согласованная запись исполнения в той же транзакции. Альтернативно нужна надлежащая сериализация конкурентных проверок. Простой «SELECT остатка, потом INSERT» не гарантирует защиту от гонки.

## 10. Критерии проверки

- **4** строки в `lesson20_orders`, **3** в `lesson20_executions`.
- Объёмы исполнений: **100, 0, 5, 0**.
- Остатки: **0, 50, 15, 10**.
- VWAP: **299.68, NULL, 7090, NULL**.
- Нет нарушений отчёта контроля из раздела 8.
- Первоначальные `dbo.trades` (**230** строк), `dbo.accounts` (**6**) и `dbo.instruments` (**12**) не изменились.

**Важно:** проект демонстрирует реляционную модель и отчёты, но не включает полноценные проверки торговых режимов, жизненного цикла поручений и конкурентного исполнения. Для настоящей брокерской системы потребуются дополнительные требования и тесты.
