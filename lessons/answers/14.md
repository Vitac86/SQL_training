# Ответы к уроку 14 — блокировки и конкурентность

[Вернуться к уроку](../14_блокировки_и_конкурентность.md)

## 1. Два @@SPID

В **двух разных окнах New Query** выполни:

```sql
SELECT @@SPID AS connection_id;
```

Ожидается **два разных числа**, потому что у окон отдельные подключения к SQL Server. Два редактора в интерфейсе — не обязательно один серверный сеанс.

## 2. Настройка RCSI и наблюдение

```sql
SELECT name, is_read_committed_snapshot_on
FROM sys.databases
WHERE name = N'TradingTraining';
```

- **0:** при стандартном `READ COMMITTED` чтение строки, изменённой незавершённым UPDATE другого подключения, обычно блокируется и может завершиться таймаутом.
- **1:** с `READ_COMMITTED_SNAPSHOT` обычный SELECT часто читает **предыдущую зафиксированную версию** без ожидания блокировки.

Это **ожидаемое поведение**, а не гарантированный результат любой конфигурации: настройки и подсказки блокировок могут влиять на наблюдение.

## 3. Почему SELECT, затем UPDATE без защиты опасны

Пусть лимит 100. Пользователи A и B одновременно читают 100 и оба решают «можно списать 80». Если между проверкой и записью нет согласования, оба могут разрешить расход на 160 при доступных 100. Нужно **атомарно** проверять и изменять лимит с корректной изоляцией/блокировками или эквивалентным механизмом.

## 4. Почему ROLLBACK освобождает ожидание

UPDATE в окне A изменил строку, но транзакция не завершилась. Пока она открыта, SQL Server может удерживать блокировку. `ROLLBACK` **отменяет изменение и завершает транзакцию**, освобождая её блокировки. Выполняй его именно **в окне A**.

```sql
-- Только в том окне, где экспериментальная транзакция ещё открыта:
ROLLBACK TRANSACTION;
```

Не запускай ROLLBACK на произвольном другом подключении.

## 5. Пример deadlock

```text
Транзакция A: удерживает строку 1 → ждёт строку 2
Транзакция B: удерживает строку 2 → ждёт строку 1
```

Обе ждут друг друга, поэтому ни одна не может продолжить сама. SQL Server обычно выбирает одну транзакцию **жертвой**, откатывает её и позволяет второй завершить работу. В приложении нужна обработка ошибки и допустимый повтор операции.

**После эксперимента:** обе сессии должны завершить учебные транзакции, а `risk_limit_rub` счёта 6 должен быть снова **500000.00**.
