# Урок 09. Проектирование и нормализация: почему таблицы именно такие

**Цель:** самостоятельно проектировать связанные таблицы и объяснять ограничения.

## Модель начинается с бизнес-фактов

Представим сырой Excel:

```text
trade_id | date | client_name | account | ticker | instrument_name | quantity | price
```

Здесь одно и то же имя клиента/инструмента повторяется на сотнях строк. Возникают **аномалии**:
- Обновление: переименование инструмента приходится исправлять во всех сделках.
- Вставка: нельзя добавить инструмент без сделки, если справочник не выделен.
- Удаление: удаляя последнюю сделку, можно потерять единственное описание инструмента.

## Нормальные формы (практическая интерпретация)

**1NF:** столбцы содержат значения согласованного типа на выбранной детализации, без повторяющихся групп вроде `ticker_1, ticker_2`. Это про структуру отношения, а не запрет строковых списков буквально во всех системах.

**2NF:** в отношении, удовлетворяющем 1NF, неключевые атрибуты зависят от **полного** кандидатного ключа, а не только его части. Например, если ключ `(trade_date, instrument_id)`, то `ticker` зависит лишь от `instrument_id` — ему место в справочнике `instruments`.

**3NF:** устраняется некорректная транзитивная зависимость неключевых атрибутов от ключа через другой неключевой атрибут. В обычной речи: информация об инструменте хранится в инструменте, не в каждой сделке. Формальные определения требуют понятий функциональной зависимости и кандидатного ключа; механическое «разнеси всё по таблицам» неверно.

**Денормализация** допустима осознанно для отчётной нагрузки, когда обеспечена согласованность. Сначала проверь исходную модель и «зерно» фактов.

## Ключи и историчность

Суррогатный ID (`instrument_id`) стабилен при переименовании тикера. Тикер — **естественный ключ**, но может измениться или оказаться неоднозначным между площадками. В промышленной модели часто нужны MIC/биржа, торговый режим, ISIN, даты действия идентификаторов.

Для «поручение → исполнения» связь 1:N: поручение описывает волю клиента, исполнения — отдельные факты совершённых сделок. Их нельзя сводить в одну таблицу с полями `fill_1`, `fill_2` и т. п.

## Практика: схема SQL Server

```sql
USE TradingTraining;
SELECT t.name AS table_name, kc.name AS pk_name
FROM sys.tables AS t
LEFT JOIN sys.key_constraints AS kc
  ON kc.parent_object_id = t.object_id AND kc.type = 'PK'
WHERE t.name IN ('trades', 'accounts', 'instruments', 'daily_prices')
ORDER BY t.name;

SELECT t.name, c.name, TYPE_NAME(c.user_type_id) AS data_type
FROM sys.tables AS t
JOIN sys.columns AS c ON c.object_id = t.object_id
WHERE t.name = 'daily_prices'
ORDER BY c.column_id;
```
