# Урок 01. Реляционная модель, таблицы и ключи

**Цель:** понять связи и ограничения, а не просто запоминать SELECT.

## Реляционная модель

Таблица представляет отношение; её строки — кортежи, столбцы — атрибуты. В практическом SQL строки могут дублироваться в **результате SELECT**, если не использовать `DISTINCT`. Поэтому не переносим все свойства математического множества на SQL без оговорок.

В нашей модели **сущности**: счёт (`accounts`), инструмент (`instruments`), сделка (`trades`). Между `accounts` и `trades` связь 1:N — одному счёту соответствует много сделок, одна сделка ссылается на один счёт.

```text
accounts.account_id (PK) 1 ---- N trades.account_id (FK)
instruments.instrument_id (PK) 1 ---- N trades.instrument_id (FK)
instruments.instrument_id (PK) 1 ---- N daily_prices.instrument_id (FK)
daily_prices (price_date, instrument_id) = составной первичный ключ
```

**PRIMARY KEY:** уникален и не NULL, идентифицирует запись. **FOREIGN KEY:** ссылается на ключ родительской таблицы и контролирует допустимые значения при записи. **UNIQUE:** запрещает повторы (нюансы с NULL зависят от СУБД). **CHECK:** бизнес-ограничение; **NOT NULL:** обязательность; **DEFAULT:** значение по умолчанию, если при INSERT оно не указано. **JOIN ≠ FOREIGN KEY:** первый извлекает связанные строки, второй обеспечивает ссылочную целостность.

## Типы данных: зачем строгость

- `INT`/ `BIGINT` — целочисленные идентификаторы и количество.
- `DECIMAL(19,4)` — фиксированная точность для цены/комиссии; `FLOAT` приближённый и опасен для точных денежных расчётов.
- `NVARCHAR(200)` — Unicode-названия; строковые литералы с кириллицей пишем `N'...' `.
- `VARCHAR(32)` — код/тикер из латиницы; `CHAR(3)` — валютный код постоянной длины.
- `DATE` — календарная дата, `DATETIME2` — дата и время (лучше, чем `DATETIME` для новых схем), `BIT` — булево значение.
- `ROWVERSION` — маркер версии строки, **не** дата и время.

Идентификатор `IDENTITY` генерируется сервером, но не означает отсутствия пропусков и не гарантирует упорядоченность бизнес-событий. Наши ID загружены из фиксированного синтетического набора.

## Посмотреть реальные ограничения

```sql
USE TradingTraining;
SELECT t.name AS table_name, c.name AS column_name,
       TYPE_NAME(c.user_type_id) AS data_type, c.is_nullable
FROM sys.tables AS t
JOIN sys.columns AS c ON c.object_id = t.object_id
WHERE t.name = 'trades'
ORDER BY c.column_id;

SELECT fk.name AS constraint_name,
       OBJECT_NAME(fk.parent_object_id) AS child_table,
       OBJECT_NAME(fk.referenced_object_id) AS parent_table
FROM sys.foreign_keys AS fk
WHERE fk.parent_object_id = OBJECT_ID(N'dbo.trades');
```

## Мини-эксперимент с CHECK и FK (без изменения результата)

```sql
BEGIN TRANSACTION;
BEGIN TRY
    INSERT INTO dbo.trades
      (trade_id, trade_date, account_id, instrument_id, side, quantity, price, commission)
    VALUES (900001, '20240109', 1, 1, 'BUY', -10, 100, 0);
END TRY
BEGIN CATCH
    SELECT ERROR_NUMBER() AS error_no, ERROR_MESSAGE() AS error_message;
END CATCH;
IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
```

Вставка **должна быть отклонена**: `CK_trades_quantity` запрещает отрицательное количество. Если после ошибочного выражения транзакция не может быть продолжена, её нужно откатить; в сложных процедурах проверяй `XACT_STATE()`.
