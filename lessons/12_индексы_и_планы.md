# Урок 12. Индексы, статистика и планы выполнения SQL Server

**Цель:** понять, почему SQL с одинаковым результатом может работать с разной скоростью.

## Логические данные и физическое хранение

Таблица — логическое отношение. SQL Server хранит записи на страницах, использует **буферный пул**, журнал транзакций и структуру индексов. **Clustered index** определяет физическую B-tree организацию данных таблицы (листовой уровень содержит строки). **Nonclustered index** — отдельная структура с ключом и указателем/кластерным ключом для доступа к строкам. Таблица без clustered index называется **heap**.

Первичный ключ и индекс — разные понятия: PK — ограничение уникальности, реализуемое индексом; **наличие FK само по себе не создаёт индекс** на дочерней таблице. В нашей учебной схеме PK по умолчанию создаётся как кластеризованный, пока не указан иной вариант и нет другого clustered index.

## Seek, scan, lookup

- **Index Seek**: навигация по диапазону ключа индекса.
- **Index/Table Scan**: последовательный просмотр индекса/таблицы; для маленьких таблиц scan может быть **оптимален**.
- **Key Lookup**: получение недостающих полей по ключу в другом индексе.
- **Covering index**: индекс содержит нужные запросу данные (ключи и при необходимости `INCLUDE`).

Оптимизатор использует статистику распределения и оценки кардинальности. Сам факт наличия индекса не гарантирует его использования.

## Практика: измерение в SSMS

Включи **Query → Include Actual Execution Plan** (обычно Ctrl+M) и сравни:

```sql
USE TradingTraining;
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT trade_id, trade_date, quantity, price
FROM dbo.trades
WHERE instrument_id = 1
ORDER BY trade_date;

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;
```

Изучи вкладку **Execution Plan** и вкладку **Messages**: логические чтения, оценки строк, операции. Затем запусти `database/04_indexes_optional.sql` и повтори запрос. **На 230 строках ожидаемого ускорения может не быть**: задача — понять план, а не получить большую цифру.

## Составные индексы и SARGability

Индекс `(instrument_id, trade_date)` полезен для фильтра по инструменту и диапазону дат. Порядок полей важен. `INCLUDE (quantity, price)` позволяет покрыть запрос без расширения ключа поиска. SARGability — способность использовать поисковый предикат по индексу.

```sql
-- Для интервала по DATE или DATETIME2 потенциально удобнее индекс:
SELECT * FROM dbo.trades
WHERE trade_date >= '20240201' AND trade_date < '20240301';

-- Функция над колонкой может мешать эффективному поиску:
SELECT * FROM dbo.trades
WHERE YEAR(trade_date) = 2024 AND MONTH(trade_date) = 2;
```

Но на реальной системе решение принимают по плану и данным. Индексы занимают место, обслуживаются при DML, могут усиливать блокировки. Индексирование — **компромисс между чтением, записью и хранением**.
