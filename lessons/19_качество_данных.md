# Урок 19. Контроль качества: как понять, что отчёт верен

**Знакомо:** SELECT, COUNT, JOIN, ключи, ограничения, группировка. **Новое:** контрольные проверки качества данных, сверка с источником, поиск дублей и потерянных записей.

## 1. SQL выполнился без ошибки — значит ли это, что отчёт верен?

Нет. Например, ошибочный JOIN, который сопоставил сделку со всеми ценами инструмента за разные даты, **может выполниться успешно**. Но результат окажется неверным: одна сделка появится много раз, а сумма комиссий вырастет искусственно.

Значит, нам нужны проверки не только синтаксиса, но и **смысла данных**.

## 2. Начнём с известных чисел

После старта `database/03_check.sql` мы знаем объём учебного набора:

```text
instruments = 12
accounts    = 6
trades      = 230
daily_prices= 429
liquidity   = 429
```

Сделаем простой контроль:

```sql
USE TradingTraining;

SELECT 'trades' AS test_name,
       COUNT(*) AS actual_rows
FROM dbo.trades;
```

Ожидаем 230. Если внезапно 229, 231 или 0 — сначала выясняем **почему**. Возможно, кто-то изменил данные, не выполнилась загрузка либо запрос считает не то.

## 3. Проверяем отсутствие дублей

Первичные ключи защищают нас от одинаковых trade_id, но SQL можно использовать и для диагностики:

```sql
SELECT trade_id, COUNT(*) AS repeated
FROM dbo.trades
GROUP BY trade_id
HAVING COUNT(*) > 1;
```

Ожидается **0 строк**. Повторов нет — в том числе потому, что PRIMARY KEY запрещает их записать. Но в импортируемом сыром файле ещё до PK могут быть дубли: там проверка понадобилась бы обязательно.

## 4. Ищем потерянные связи

```sql
SELECT t.trade_id, t.instrument_id
FROM dbo.trades AS t
LEFT JOIN dbo.instruments AS i
  ON i.instrument_id = t.instrument_id
WHERE i.instrument_id IS NULL;
```

Ожидается **0 строк**: FK в нашей модели не должен позволить записать сделку на несуществующий инструмент. Если бы импортировали данные без таких ограничений или временно отключили их, этот контроль мог бы выявить нарушение.

## 5. Тестируем логику JOIN

Сравни количество строк до и после **правильного** соединения:

```sql
SELECT COUNT(*) AS base_rows
FROM dbo.trades;

SELECT COUNT(*) AS joined_rows
FROM dbo.trades AS t
JOIN dbo.instruments AS i ON i.instrument_id = t.instrument_id
JOIN dbo.accounts AS a ON a.account_id = t.account_id;
```

Оба числа должны быть **230**: у каждой сделки один действующий инструмент и один действующий счёт.

Теперь намеренно **неправильное** сопоставление с ценами:

```sql
SELECT COUNT(*) AS wrong_join_rows
FROM dbo.trades AS t
JOIN dbo.daily_prices AS p
  ON p.instrument_id = t.instrument_id;
```

Число может быть намного больше 230 — к каждой сделке присоединяются разные даты цен. Исправление: добавить `AND p.price_date = t.trade_date`. Смысл проверки: **сравнивай количество строк до и после JOIN** и понимай, что означает одна строка.

## 6. Что такое «зерно отчёта»

Запрос «комиссия по счёту и по дате» должен давать одну строку на пару `(account_id, trade_date)`. Если получилась одна строка на каждую отдельную сделку, это **другой уровень детализации**.

```sql
SELECT account_id, trade_date,
       COUNT(*) AS trade_count,
       SUM(commission) AS fee_total
FROM dbo.trades
GROUP BY account_id, trade_date
ORDER BY account_id, trade_date;
```

Прежде чем делать отчёт, запиши словами, **что представляет одна строка результата**. Это предотвращает большую часть ошибок в аналитике.

## 7. Какие ещё проверки нужны в реальной брокерской БД

- Значения цены и количества неотрицательны/допустимы по правилам инструмента.
- Внешние идентификаторы сделок уникальны в рамках источника.
- Нет пропущенных дат, противоречивых статусов и неожиданных остатков.
- Итоги сверяются с торговой или учётной системой.
- Модель учитывает валюты, лоты, корпоративные действия и начальные позиции.
- У импорта есть правила, что делать с повторно пришедшими данными (**идемпотентность** — повторный приём не должен дублировать факт).

Проверки разумно автоматизировать, но сперва их нужно **сформулировать и понять вручную**.
