# Урок 20. Итоговый проект: поручения и исполнения сделок

**Цель:** соединить навыки всего курса: таблицы, ключи, ограничения, INSERT, JOIN, группировки, даты, транзакции и проверки качества. Делай по этапам; не пытайся написать всё за один заход.

**Важно:** работа учебная, отдельные таблицы `dbo.lesson20_orders` и `dbo.lesson20_executions`. Исходные `dbo.trades`, `dbo.accounts`, `dbo.instruments` не меняем.

## 1. Сначала поймём процесс без SQL

Клиент отправил поручение: «Купить 100 акций SBER по цене не выше 300».

Брокер может исполнить его:
- сразу одной сделкой на 100;
- двумя сделками, например 40 и 60;
- только на 40, а остальное не исполнить;
- не исполнить вообще.

**Поручение** — что клиент поручил сделать. **Исполнение** — фактическая часть выполненной сделки. Одно поручение → много исполнений (1:N).

```text
orders:    order_id=1, ticker=SBER, quantity=100
           │
           ├── executions: quantity=40, price=299.5
           └── executions: quantity=60, price=299.8
```

## 2. Составь проект таблиц на бумаге

**Поручения**:
- `order_id` — PK;
- `external_order_id` — уникальный номер из внешней системы;
- `account_id` — FK → accounts;
- `instrument_id` — FK → instruments;
- `side` — BUY/SELL;

- `limit_price` — положительное десятичное или NULL;
- `submitted_at` — дата/время;
- `status` — например NEW, PARTIAL, FILLED, CANCELED.

**Исполнения**:
- `execution_id` — PK;
- `order_id` — FK → orders;
- `executed_at` — дата/время;
- `quantity` — положительное целое;
- `price` — положительное десятичное;
- `commission` — неотрицательное число.

## 3. Создай таблицы и проверь ограничения

В отдельном файле, например `project.sql`, напиши два `CREATE TABLE`. Подсказка:

```sql
-- Начало твоего CREATE TABLE; допиши самостоятельно:
-- CREATE TABLE dbo.lesson20_orders (
--     order_id INT NOT NULL PRIMARY KEY,
--     account_id INT NOT NULL REFERENCES dbo.accounts(account_id),
--     ...
-- );
```

Используй `CHECK` для положительных количеств, разрешённых сторон и цен; `UNIQUE` для внешнего ID. Подумай, какие поля должны быть `NOT NULL`. Установка FK между поручением и исполнением гарантирует, что не будет исполнения на несуществующее поручение.

**Но:** один FK не гарантирует, что сумма исполнений не превысит количество поручения. Это уже бизнес-правило, которое требует дополнительной логики.

## 4. Загрузим маленький набор данных

Создай INSERT для четырёх ситуаций:

1. Поручение `order_id=1` BUY SBER 100 — два исполнения 40 и 60.
2. Поручение `order_id=2` SELL GAZP 50 — пока **нет исполнений**.
3. Поручение `order_id=3` BUY LKOH 20 — исполнено только 5.
4. Поручение `order_id=4` BUY SBER 10 — отменено без исполнений.

Для всех используй существующие `account_id` и `instrument_id`. Применяй значения даты и времени вроде `'2024-01-09T10:15:00'` для `DATETIME2`.

## 5. Первый отчёт: список всех поручений

Напиши SELECT через JOIN:
- номер поручения;
- имя счёта;
- тикер;
- side и количество;
- статус.

Ожидается **четыре строки** — по одной на поручение. Без исполнения поручения тоже остаются.

## 6. Второй отчёт: исполнено и осталось

Теперь LEFT JOIN к `lesson20_executions` и GROUP BY по поручению:

```text
order_id | ordered_qty | filled_qty | remaining_qty
1        | 100         | 100        | 0
2        | 50          | 0          | 50
3        | 20          | 5          | 15
4        | 10          | 0          | 10
```

Подсказка: `COALESCE(SUM(e.quantity), 0)` для пустых исполнений. В GROUP BY обязательно учти номер и объём поручения. **Нельзя** автоматически заменить отсутствие цены исполнения нулевой ценой: если сделки не было, VWAP отсутствует.

## 7. Третий отчёт: средневзвешенная цена исполнений

Используй:

```sql
SUM(CAST(e.quantity AS DECIMAL(19,4)) * e.price)
  / NULLIF(SUM(CAST(e.quantity AS DECIMAL(19,4))), 0)
```

Это средняя взвешенная цена исполнения **в рамках одного поручения**. При отсутствии исполнений результат NULL. Обязательно ограничь расчёт одной однородной группой — не смешивай разные инструменты и валюты.

## 8. Проверка качества

Напиши запрос, который пометит:
- исполнено **больше**, чем поручено;
- статус FILLED, хотя исполнено **меньше**, чем поручено;
- статус NEW при уже существующих исполнениях;
- дубли `external_order_id`;
- отрицательные quantity/price.

Некоторые нарушения база отсеет CHECK/FK/UNIQUE автоматически. Другие являются **межстрочными правилами** и потребуют отчёта или серверной бизнес-логики.

## 9. Что делать при двух одновременных исполнениях

Представь остаток 20. Два обработчика одновременно читают остаток и каждый пытается исполнить 15. Если просто `SELECT` и потом `INSERT`, обе операции могут пройти и суммарно превысить поручение.

Предложи механизм: **одна транзакция** проверяет остаток и добавляет исполнение, при этом конкурентная операция не должна одновременно использовать тот же остаток. На профессиональном уровне это реализуют соответствующими блокировками/изоляцией, атомарным обновлением или другим сериализующим механизмом. Просто `CHECK(quantity > 0)` не решает гонку.
