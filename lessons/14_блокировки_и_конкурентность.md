# Урок 14. Два пользователя, одна запись: блокировки и изоляция

**Знакомо:** транзакции, COMMIT и ROLLBACK из урока 13. **Новое:** блокировки, параллельные подключения, уровень изоляции и чтение версий.

## 1. Почему одновременно работать сложнее

Представь два сотрудника: оба читают один и тот же доступный лимит клиента, а затем каждый пытается его потратить. Если система просто читает значение и позже записывает новое, может возникнуть **гонка**: обе операции думают, что денег достаточно.

База должна упорядочивать или согласовывать конкурирующие изменения. Для этого используются **блокировки** (временные ограничения доступа к данным) и, при некоторых настройках, **версии строк** (сохранённые предыдущие состояния для чтения).

## 2. В SSMS откроем два независимых окна

Нажми **New Query** дважды, подключи оба к локальному SQL Server. Назови их мысленно «Окно A» и «Окно B». Каждое окно обычно имеет собственное подключение. Проверь:

```sql
SELECT @@SPID AS connection_id;
```

`@@SPID` — номер текущего серверного подключения. Числа в двух окнах должны отличаться.

## 3. Посмотреть настройку нашей базы

```sql
SELECT name, is_read_committed_snapshot_on
FROM sys.databases
WHERE name = 'TradingTraining';
```

Пока достаточно: **0** обычно означает чтение READ COMMITTED с блокировками; **1** — с версиями строк (RCSI). Это помогает предсказать эксперимент ниже.

## 4. Окно A: изменим и специально не завершим транзакцию

В **окне A** выполни:

```sql
USE TradingTraining;
BEGIN TRANSACTION;

UPDATE dbo.accounts
SET risk_limit_rub = risk_limit_rub + 1
WHERE account_id = 6;
```

**Пока не нажимай COMMIT и не закрывай окно.** Значение изменено в незавершённой транзакции. Другие подключения не должны видеть его как зафиксированное состояние.

## 5. Окно B: попробуем прочитать ту же строку

Во **втором** окне выполни:

```sql
USE TradingTraining;
SET LOCK_TIMEOUT 3000;

SELECT account_id, risk_limit_rub
FROM dbo.accounts WHERE account_id = 6;

SET LOCK_TIMEOUT -1;
```

`LOCK_TIMEOUT 3000` — «не ждать блокировку дольше 3 секунд» (миллисекунды). Если выполнение завершилось ошибкой таймаута **до последнего SET**, отдельно выполни `SET LOCK_TIMEOUT -1;`, чтобы вернуть обычное ожидание.

Что увидишь:
- Если у базы `is_read_committed_snapshot_on=0`, чтение **может ждать/получить timeout** из-за блокировки изменённой строки.
- Если `=1`, чтение может сразу показать **старое подтверждённое значение** из версии строки.

Наблюдение может зависеть от других настроек. Ни один из вариантов не означает, что SQL Server «сломался».

**СРАЗУ вернись в окно A и выполни:**

```sql
ROLLBACK TRANSACTION;
```

Убедись, что лимит снова 500000.00. Не оставляй транзакцию открытой.

## 6. Что такое уровень изоляции

Это правило: **какие изменения других транзакций разрешено видеть текущему запросу и какие гарантии даются**.

Основные названия, с которыми предстоит сталкиваться:
- `READ COMMITTED` — не читаем чужие незавершённые изменения; может работать на блокировках или версиях.
- `READ UNCOMMITTED` — допускает «грязное» чтение. Это опасно для остатков и риск-показателей.
- `REPEATABLE READ` — сильнее удерживает стабильность прочитанных строк.
- `SERIALIZABLE` — более строгие гарантии, но может давать больше ожиданий.
- `SNAPSHOT` — чтение согласованного снимка версий с собственными правилами конфликта изменений.

Эти уровни будем применять в будущем по конкретным задачам, а не угадывать «самый быстрый».

## 7. Дедлок простыми словами

Допустим, операция A удерживает строку 1 и ждёт строку 2, а операция B удерживает строку 2 и ждёт строку 1. Получается замкнутый круг ожидания — **deadlock**. SQL Server распознаёт его и прерывает одну из транзакций, чтобы другая могла продолжиться.

Поэтому полезны короткие транзакции, единый порядок работы с ресурсами и корректная обработка повторных попыток. **Не используй NOLOCK** как универсальное решение — можно прочитать неверные финансовые данные.

## Задания

1. В двух окнах посмотри `@@SPID`. Почему это два разных подключения?
2. Сравни настройку `is_read_committed_snapshot_on` с поведением чтения.
3. Объясни, почему «сначала SELECT остатка, потом UPDATE остатка» без защиты от конкуренции опасно.
4. Почему ROLLBACK в окне A освобождает ситуацию после эксперимента?
5. Нарисуй пример deadlock с двумя строками и двумя транзакциями.

**Самопроверка:** после эксперимента нет открытой учебной транзакции; `ACC-DORMANT` сохранил исходный лимит. Ты понимаешь, что **изоляция** — не абстрактное слово, а поведение разных одновременных пользователей.
