# Урок 05. Создаём свою таблицу и сами задаём ограничения

**Знакомо:** таблица, типы данных, PK/FK, WHERE. **Новое:** `CREATE TABLE`, `INSERT`, `NOT NULL`, `CHECK`, `CONSTRAINT`. **Именно здесь** мы впервые самостоятельно задаём ограничения.

## 1. Зачем создавать ещё одну таблицу

До сих пор мы работали с **готовой** базой, которую создали скрипты из папки `database`. Поэтому правило «`quantity` должно быть положительным» действительно возникло словно из ниоткуда. Теперь сделаем то же самое на простой таблице, которую ты сам создашь, и только потом вернёмся к `dbo.trades`.

Представим список маленьких учебных поручений:

```text
order_id | ticker | quantity
1        | SBER   | 10
2        | GAZP   | 20
```

Каждому поручению нужен уникальный номер, тикер и положительное количество.

## 2. CREATE TABLE — создаём пустую таблицу

В **новом окне запроса SSMS** выполни только этот фрагмент **один раз**:

```sql
USE TradingTraining;

CREATE TABLE dbo.lesson05_orders (
    order_id INT NOT NULL
        CONSTRAINT PK_lesson05_orders PRIMARY KEY,

    ticker VARCHAR(20) NOT NULL,

    quantity INT NOT NULL
        CONSTRAINT CK_lesson05_quantity CHECK (quantity > 0)
);
```

Разберём построчно:

- `CREATE TABLE dbo.lesson05_orders` — создай таблицу с именем `lesson05_orders`.
- `order_id INT` — целое число, номер записи.
- `PRIMARY KEY` — номера не должны повторяться и не могут быть пустыми.
- `ticker VARCHAR(20)` — текст до 20 символов.
- `quantity INT` — целое число.
- `NOT NULL` — поле обязательно должно быть заполнено.
- `CHECK (quantity > 0)` — **сервер разрешает только количество больше нуля**.
- `CONSTRAINT CK_lesson05_quantity` — мы **дали правилу имя** `CK_lesson05_quantity` для удобства поиска.

Это и есть определение структуры. Правило хранится **в SQL Server**, а не в последующем INSERT.

**Почему мы не удаляем таблицу перед каждым запуском?** Для обучения важно видеть, что таблица сохраняется. Если повторно выполнить `CREATE TABLE`, SQL Server сообщит, что такое имя уже существует. Это не сбой сервера: таблица создана с первого раза.

## 3. Сразу посмотрим на результат в SSMS

Слева: `TradingTraining → Tables` → правой кнопкой **Обновить**. Появится `dbo.lesson05_orders`.

Раскрой её:

- **Columns / Столбцы** — увидишь `order_id`, `ticker`, `quantity`.
- **Keys / Ключи** — здесь ключ первичной записи.
- **Constraints / Ограничения** — найди `CK_lesson05_quantity`.

А ещё: правой кнопкой по таблице → **Script Table as → CREATE To → New Query Editor Window**. SQL Server покажет SQL, соответствующий структуре. **Не выполняй полученный скрипт**, просто посмотри на `CHECK` и `PRIMARY KEY`.

## 4. INSERT: добавляем одну правильную строку

```sql
INSERT INTO dbo.lesson05_orders (order_id, ticker, quantity)
VALUES (1, 'SBER', 10);
```

Читаем: «в таблицу orders, в перечисленные столбцы, добавь значения 1, SBER, 10». Сверимся:

```sql
SELECT * FROM dbo.lesson05_orders;
```

Появилась одна запись. **INSERT меняет базу**, в отличие от SELECT. Если выполнить тот же INSERT второй раз, будет ошибка: номер 1 уже занят.

## 5. А теперь попробуем неправильное количество

Выдели и выполни **только** этот INSERT:

```sql
INSERT INTO dbo.lesson05_orders (order_id, ticker, quantity)
VALUES (2, 'GAZP', -10);
```

Ожидается **ошибка в «Сообщениях / Messages»**. SQL Server скажет, что INSERT нарушает ограничение `CK_lesson05_quantity`.

Почему? Мы сами написали `CHECK (quantity > 0)` при создании таблицы. `-10 > 0` — неправда, значит строку записать нельзя.

Проверь:

```sql
SELECT * FROM dbo.lesson05_orders;
```

В таблице **по-прежнему только запись с order_id = 1**. Неудачная команда INSERT не записала недопустимую строку. Для проверки ограничений пока не нужны `TRY/CATCH` и `ROLLBACK`: сейчас мы учимся понимать **первопричину ошибки**.

## 6. Ещё два независимых испытания

**Повторим номер** (нарушение PRIMARY KEY):

```sql
INSERT INTO dbo.lesson05_orders (order_id, ticker, quantity)
VALUES (1, 'LKOH', 5);
```

Не сработает: `order_id = 1` уже есть.

**Не укажем обязательное поле** (нарушение NOT NULL):

```sql
INSERT INTO dbo.lesson05_orders (order_id, ticker, quantity)
VALUES (3, NULL, 5);
```

Не сработает: `ticker` не может быть NULL. В обоих случаях другие строки остаются на месте.

Запиши различие: `PRIMARY KEY` — уникальный идентификатор; `NOT NULL` — обязательность; `CHECK` — правило допустимого значения.

## 7. Где задано ограничение в исходной таблице trades?

Открой файл `database/01_schema.sql` (это текст, который мы **уже запускали при подготовке базы**). Найди фрагмент:

```sql
quantity BIGINT NOT NULL
    CONSTRAINT CK_trades_quantity CHECK (quantity > 0),
```

Он находится внутри `CREATE TABLE dbo.trades`. Мы не просто попросили «проверять количество» в SELECT: **мы задали правило при создании таблицы**.

Для проверки можно запросить список правил из специального каталога SQL Server:

```sql
SELECT name, definition
FROM sys.check_constraints
WHERE parent_object_id = OBJECT_ID('dbo.trades');
```

Это **необязательная** команда: `sys.check_constraints` — системное представление с описанием правил; его устройство изучим позднее. Достаточно увидеть `CK_trades_quantity`.

Теперь ясно, почему этот запрос из старой версии курса **не должен выполниться**:

```sql
-- НЕ ВЫПОЛНЯЙ без необходимости: это демонстрация недопустимой записи.
-- INSERT INTO dbo.trades (..., quantity, ...) VALUES (..., -10, ...);
```

Минусовая сделка нарушает CHECK ещё **до** появления записи в таблице.

## 8. Что делать с учебной таблицей

Оставь `dbo.lesson05_orders` как лабораторию для повторения либо **после всех упражнений** удали **именно её**:

```sql
DROP TABLE dbo.lesson05_orders;
```

`DROP TABLE` удаляет **таблицу целиком вместе с данными и правилами**. Используй только точное имя `lesson05_orders`, не `trades` и не `instruments`. Команда необратима обычным SELECT.

## Задания

1. Создай ещё одну корректную строку `(4, 'MOEX', 15)`, посмотри её через SELECT.
2. Попробуй `quantity = 0`. Что нарушится?
3. Попробуй `order_id = NULL`. Что нарушится?
4. Назови три места, где можно увидеть правило CHECK: SQL-код создания таблицы, SSMS Object Explorer и системный запрос.
5. Объясни человеку без SQL: почему `CHECK` — не то же самое, что `WHERE`?

**Самопроверка:** `quantity = 0` нарушает CHECK, `order_id = NULL` нарушает первичный ключ/обязательность; `WHERE` выбирает строки при чтении, а `CHECK` решает, можно ли записать значение.
