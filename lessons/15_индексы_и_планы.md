# Урок 15. Индексы и планы: как SQL Server ищет данные

**Знакомо:** WHERE отбирает нужные строки, JOIN связывает таблицы. **Новое:** индекс, план выполнения, scan/seek, базовая проверка производительности.

## 1. Представь книгу на тысячу страниц

Тебе нужно найти слово «маржа»:
- **Без указателя** — придётся листать страницы.
- **С указателем в конце книги** — сразу найдёшь нужную страницу.

В БД аналог указателя — **индекс**: отдельная структура, которая помогает SQL Server находить строки. Это не новая таблица со «второй копией всего подряд»; в индексе организованы ключи поиска и сведения, позволяющие попасть к нужным данным.

Но индекс **не бесплатен**: он занимает место и требует дополнительной работы при вставке, изменении и удалении данных.

## 2. Простой запрос, который можно искать по индексу

```sql
USE TradingTraining;

SELECT trade_id, instrument_id, trade_date, price
FROM dbo.trades
WHERE instrument_id = 1
ORDER BY trade_date;
```

Если таблица маленькая, SQL Server может просто прочитать её целиком. В нашем наборе **230 сделок**, поэтому такой способ нередко разумнее, чем сложный поиск по индексу. Это не ошибка.

## 3. Где в SSMS посмотреть индексы

В Обозревателе объектов открой `TradingTraining → Tables → dbo.trades → Indexes / Индексы`.

В нашей исходной схеме первичный ключ `trade_id` реализуется индексом. Но **первичный ключ и индекс — разные понятия**:
- **PK** говорит: «каждая строка должна иметь уникальный ключ».
- **Индекс** помогает хранению/поиску. Он может быть и не уникальным.

SQL Server обычно создаёт индекс для PK. А вот внешний ключ на дочерней таблице **не означает автоматического создания индекса**.

## 4. План выполнения — маршрут, который выбрал сервер

Запусти в SSMS следующий запрос, но **перед F5** включи пункт **Query → Include Actual Execution Plan** (обычно **Ctrl+M**):

```sql
SELECT trade_id, trade_date, price
FROM dbo.trades
WHERE instrument_id = 1
ORDER BY trade_date;
```

После выполнения рядом с «Результатами» появится вкладка **План выполнения / Execution Plan**.

План — это ответ на вопрос «**как** SQL Server решил получить строки»:
- **Scan** — просмотр набора страниц/записей.
- **Seek** — направленный поиск по индексу.
- **Sort** — отдельная сортировка, если она нужна.

Не пугайся картинок и процентов. На этом этапе достаточно увидеть, что **один и тот же SELECT может выполняться разными способами**.

## 5. Составной индекс: важен порядок полей

Если запрос часто ищет сделки **по инструменту и дате**, полезный вариант индекса:

```sql
CREATE NONCLUSTERED INDEX IX_trades_instrument_date
ON dbo.trades(instrument_id, trade_date);
```

В курсе уже есть **безопасный повторно запускаемый** файл `database/04_indexes_optional.sql`. Для практики лучше запустить именно его **после того, как посмотришь план до создания индексов**, чтобы не получить ошибку повторного имени.

Почему два поля? Сначала отбираем нужный `instrument_id`, затем диапазон `trade_date` внутри него. Упорядоченность полей индекса имеет значение.

## 6. Почему функция над датой может мешать поиску

Сравни два условия:

```sql
-- Первый способ:
SELECT trade_id FROM dbo.trades
WHERE trade_date >= '20240201' AND trade_date < '20240301';

-- Второй способ:
SELECT trade_id FROM dbo.trades
WHERE YEAR(trade_date) = 2024 AND MONTH(trade_date) = 2;
```

Они выбирают тот же февраль, но первый может быть удобнее для поиска по индексу даты: не требуется вычислять YEAR/MONTH для каждой проверяемой записи. Такие условия называют **SARGable** — пригодные для эффективного поиска по ключу индекса.

**Не делай вывод о скорости по одному слову «Seek».** Сравни реальный план, число прочитанных страниц и затраченное время на достаточно больших данных.

## 7. Посмотрим число логических чтений

```sql
SET STATISTICS IO ON;

SELECT trade_id, trade_date, price
FROM dbo.trades
WHERE instrument_id = 1;

SET STATISTICS IO OFF;
```

В «Сообщениях» увидишь статистику **logical reads** — сколько страниц сервер логически считал. Это один из способов сравнивать запросы. На крошечной базе улучшение может не проявиться.
