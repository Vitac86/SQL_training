# Урок 18. Резервная копия: как не потерять базу

**Знакомо:** данные сохраняются в SQL Server, UPDATE/DELETE меняют их, а ROLLBACK помогает **до COMMIT**. **Новое:** backup, restore, модель восстановления, RPO и RTO.

## 1. Почему одного ROLLBACK мало

В уроке 08 мы легко отменяли незавершённые операции. Но если пользователь уже сделал COMMIT, то обычным ROLLBACK вернуть изменения нельзя. А если сломался диск или произошла другая авария — нужна копия, из которой можно **восстановить базу**.

**Резервное копирование (backup)** — создание копии данных и служебной информации, необходимой для восстановления. **Restore** — сам процесс восстановления из этой копии.

Это не просто экспорт в CSV: CSV не хранит индексы, ключи, ограничения и много другой информации, нужной для полноценного возвращения БД к работе.

## 2. Делаем полную копию через знакомый Object Explorer

В SSMS:

1. `Databases → TradingTraining`.
2. Правой кнопкой по базе → **Tasks → Back Up... / Задачи → Создать резервную копию**.
3. Выбери тип **Full / Полная**.
4. Посмотри, куда будет записан файл `.bak`. Важно, чтобы этот путь был доступен **службе SQL Server**, а не только SSMS.
5. Выполни создание и прочитай сообщение об успешном завершении.

**Сначала проверь свободное место и путь.** На локальном учебном сервере обычно удобно использовать рекомендованную сервером папку Backup.

## 3. Почему SQL Server должен видеть папку

Вспомни урок 00: SSMS — интерфейс, SQL Server — программа, которая фактически работает с файлами. Бэкап создаёт **серверная служба**. Поэтому если SSMS подключён к другому компьютеру, путь `C:\\SQL` у тебя и путь `C:\\SQL` на сервере — это **разные места**.

Путь по умолчанию можно узнать:

```sql
SELECT CAST(SERVERPROPERTY('InstanceDefaultBackupPath') AS NVARCHAR(4000))
       AS backup_folder;
```

Только посмотри его; команда ничего не меняет.

## 4. Проверка копии и восстановление

Команда `RESTORE VERIFYONLY` проверяет доступность и структуру резервной копии, но **не равна тестовому восстановлению**. Надёжная практика — периодически разворачивать копию в **отдельной тестовой базе**, не поверх рабочей.

Не пытайся выполнить RESTORE на `TradingTraining` без понимания параметров — можно повредить текущую учебную среду. Для восстановления в новую базу могут потребоваться `RESTORE FILELISTONLY` и `WITH MOVE`, потому что в копии содержатся логические имена и исходные пути к файлам.

## 5. Три типа резервных копий

- **Full** — полная копия базы.
- **Differential** — изменения относительно базовой полной копии.
- **Transaction log** — копия журнала транзакций в подходящей модели восстановления и при правильной цепочке резервного копирования.

У SQL Server есть **recovery model**: SIMPLE, FULL и BULK_LOGGED. Полный бэкап можно делать и при SIMPLE. Для восстановления по цепочке лог-бэкапов нужна соответствующая модель и организованное резервирование.

```sql
SELECT name, recovery_model_desc
FROM sys.databases
WHERE name = 'TradingTraining';
```

## 6. RPO и RTO человеческим языком

- **RPO** — сколько данных по времени допускается потерять: например, «не более 5 минут операций».
- **RTO** — за какое время система должна снова работать: например, «не более 30 минут».

Из этого следуют требования к частоте копий и тестам восстановления. Часто делать backup бесполезно, если невозможно быстро его вернуть.
