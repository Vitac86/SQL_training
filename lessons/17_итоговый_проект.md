# Урок 17. Итоговый проект: поручения, исполнения и отчётность

**Задача:** самостоятельно расширить модель, чтобы отслеживать **волю клиента** (поручение) и **фактические исполнения**. Используй отдельные учебные таблицы (`dbo.orders_demo`, `dbo.executions_demo`), не меняй существующие сделки.

## Бизнес-сценарий

Клиент подаёт поручение на покупку или продажу инструмента. Поручение имеет внешний идентификатор, счёт, инструмент, сторону, количество, цену-лимит (если применима), дату, статус. Одно поручение может быть исполнено несколькими частями, отменено без исполнения или частично исполнено.

**Важно:** «поручение» и «сделка» — разные факты и не должны храниться в одной строке с повторяющимися колонками `fill_1, fill_2`.

## Требования к схеме

Спроектируй:
- `orders_demo` с PK `order_id`, UNIQUE `external_order_id`, FK `account_id` и `instrument_id`, `side` (BUY/SELL), `quantity` > 0, `limit_price` NULL для рыночных поручений, `submitted_at` `DATETIME2`, `status`.
- `executions_demo` с PK `execution_id`, FK `order_id`, `executed_at`, `quantity` > 0, `price` > 0, `commission` >= 0.
- Допустимые статусы (например, NEW / PARTIAL / FILLED / CANCELED), но не пытайся моделировать жизненный цикл только одним CHECK: допустимые **переходы** потребуют отдельной бизнес-логики и транзакций.

**Оговорка:** для реального рынка нужны дополнительные атрибуты: venue, валюта цены и расчёта, лотность, тип инструмента, корпоративные действия, события отмены/изменения, риск-контроль. Это учебный упрощённый проект.

## Тестовый набор

Создай минимум:
1. Два исполненных поручения (у одного два частичных исполнения).
2. Одно поручение без исполнения.
3. Одно частично исполненное поручение.
4. Одну попытку создать исполнение на несуществующее поручение (должна провалиться по FK).
5. Одну попытку записать отрицательное количество (должна провалиться по CHECK).

## Запросы, которые нужно написать

1. Список поручений с названием счёта и тикером через JOIN.
2. Объём исполнений и средневзвешенную цену по каждому поручению, включая поручения без исполнения (LEFT JOIN, COUNT по дочернему PK, NULLIF).
3. Остаток неисполненного количества и флаг «исполнено больше, чем разрешено».
4. Последнее исполнение по поручению через ROW_NUMBER или OUTER APPLY.
5. Количество поручений по статусам и суммарную комиссию.
6. Контроль расхождений `status='FILLED'` при неполном количестве исполнений.

## Транзакция и конкуренция

Опиши, как защищать от двух одновременных исполнений, превышающих суммарный объём поручения. Один FK не обеспечивает `SUM(execution.quantity) <= orders.quantity`. Нужна атомарная проверка и запись с адекватной изоляцией/блокировками или эквивалентный сериализующий механизм.

## Критерии приёмки

- Скрипты `CREATE TABLE` и тестовые `INSERT` повторяемы на чистой учебной базе.
- Понятные PK/FK/CHECK/UNIQUE, отсутствуют лишние дубли описательных данных.
- Отчёты показывают и «пустые» поручения; отсутствие исполнения не превращается в фиктивный fill.
- Определено «зерно» каждого отчёта; соединения не завышают суммы.
- Тесты сознательно проверяют ограничения и бизнес-ошибки.
- Скрипты не удаляют или не изменяют исходные `trades`, `accounts` и `instruments`.

**Результат:** собственная маленькая модель OLTP + аналитические SQL-запросы и объяснение каждого архитектурного решения.
