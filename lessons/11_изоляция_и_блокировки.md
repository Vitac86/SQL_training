# Урок 11. Изоляция, блокировки и конкурирующие операции

**Цель:** понимать, почему правильный SELECT и UPDATE могут вести себя по-разному при двух пользователях.

## Суть конкурентности

Транзакции могут пересекаться по времени. Типовые аномалии: **dirty read** (чтение неподтверждённого), **non-repeatable read** (повторное чтение изменилось), **phantom** (изменилось множество строк), **lost update** (потерянное обновление). Изоляция ограничивает наблюдаемое поведение, но уровень изоляции сам по себе не заменяет проверки бизнес-ограничений.

SQL Server поддерживает `READ UNCOMMITTED`, `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`, а также версионирование (`SNAPSHOT`; `READ_COMMITTED_SNAPSHOT` — опция базы). При включённом RCSI чтения READ COMMITTED используют версии строк; без RCSI обычно используют разделяемые блокировки чтения.

## Проверить настройки

```sql
USE TradingTraining;
SELECT name, is_read_committed_snapshot_on,
       snapshot_isolation_state_desc
FROM sys.databases WHERE name = DB_NAME();

DBCC USEROPTIONS;
```

## Эксперимент в двух окнах SSMS

**Окно A:** (выполни, но не фиксируй)

```sql
USE TradingTraining;
BEGIN TRANSACTION;
UPDATE dbo.accounts
SET risk_limit_rub = risk_limit_rub + 1
WHERE account_id = 6;
-- Не COMMIT! Держим транзакцию открытой для наблюдения.
```

**Окно B:** (новое подключение, выполнить отдельно)

```sql
USE TradingTraining;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET LOCK_TIMEOUT 3000;
SELECT risk_limit_rub FROM dbo.accounts WHERE account_id = 6;
SET LOCK_TIMEOUT -1;
```

Если RCSI **выключен**, чтение может дождаться завершения UPDATE или получить timeout (ошибка 1222). Если RCSI **включён**, SELECT может прочитать предыдущую зафиксированную версию — это нормальное поведение. **Вернись в окно A и обязательно выполни `ROLLBACK TRANSACTION;`**. Если окно B прервалось до возврата таймаута, настройка `LOCK_TIMEOUT` может остаться; выполни `SET LOCK_TIMEOUT -1;` отдельно.

## Deadlock и блокировки

Deadlock: две транзакции удерживают ресурсы, нужные друг другу. SQL Server выбирает жертву и откатывает её; приложение должно корректно повторять допустимые операции. Минимизируй длительность транзакций, меняй ресурсы в согласованном порядке, индексируй предикаты, не смешивай транзакцию с долгим внешним вызовом.

Для условного резерва лимита важны **атомарный UPDATE с условием** и проверка `@@ROWCOUNT`, а не `SELECT` с последующим незащищённым UPDATE. При необходимости изучают `UPDLOCK`, `HOLDLOCK`, `ROWVERSION`, `SERIALIZABLE` — всегда с учётом блокировок и производительности.
